## 13. Capacity engine (P9)

The router's economics depend on which pool pays. Pools have different shapes, and the engine models them explicitly:

| Pool kind | Example | Unit | Reset shape |
|---|---|---|---|
| Subscription windows | Claude Max 5x/20x | tokens (est.) | 5-hour rolling + weekly cap |
| Metered credits | Copilot on AI-Credit billing (post-Jun 2026) | credits ≈ $ | monthly allowance + PAYG |
| Legacy request pools | Copilot annual plans | premium requests × per-model multiplier | monthly |
| API keys | Anthropic/OpenAI direct | dollars | none (budget only) |
| Local | home-server models via an OpenAI-compatible endpoint | unlimited | none (hardware-bound) |

**Estimation sources**, in trust order: (1) rate-limit signals from the CLIs — ground truth; a `RateLimited` outcome immediately marks the pool exhausted, demotes or parks frontier-hungry tasks, and sets a retry-at-reset timer; (2) self-metering of everything the engine spawned; (3) ccusage-style parsing of local agent logs, which captures the user's *interactive* sessions drawing from the same pool; (4) optionally, provider usage endpoints where they exist — treated as fragile (several are reverse-engineered and break silently) and never load-bearing. Estimates are always conservative: a per-pool `safety_margin` (usage on other machines is invisible to local log parsing) and a `reserve` floor that keeps headroom for the user's own interactive work.

**Rate limits and resets, as built (2026-11-14).** Source 1 is narrower than the paragraph above reads. Beside a fixed list of phrases (`5-hour limit reached`, `usage limit`, Copilot's credit wording, API errors), a failed attempt is `RateLimited` when its text says it hit a quota window's limit (`You've hit your 5-hour limit`; any number of hours, `session` or `weekly`), or the limit of one of Claude's four model names — Opus, Sonnet, Haiku, Fable — with a reset after it (`You've hit your Fable limit · resets Nov 14, 9am (UTC)`). A model name without a reset, or any other word (`context`, `token`, `request`), is an ordinary task failure. The reset recorded as `pool_exhausted.reset_at`, and carried into `capacity_snapshot`, is read only from the limit's own text: the `resets` that follows the recognised limit on its line, or, when nothing after the limit on its line is a reset, a `resets` that begins the very next line. A reset with no such limit before it — `MCP cache resets 9am (UTC)` alone, or on a later line — is never read, and when the limit's own reset cannot be read (a zone other than UTC, a malformed time) none is recorded and no other reset stands in. Stderr, when that is what signalled the limit, is read before the attempt's reason, and the first of the two that holds a recognised limit decides: the reason is read only when the stderr holds none. Only Claude Code's text is read, since no other vendor's reset format is known, so every other agent records none. The messages give no year, and the short form no date, so the reset is the occurrence nearest the moment the text is read: a limit read a second after its reset keeps that reset, not one a day ahead. A pool gets one `pool_exhausted` per distinct reset. A repeat refusal naming the same reset, or none, writes nothing; the fold, and so a replay or resume, reports the latest signal's reset; a rate-limited deferral with no signal of its own keeps the known reset; and a success retires the pool, reset and all, so the next refusal writes one again. Both engines now record `pool_exhausted` under the same rules. The schema-4 engine appends it before the rate-limited settlement, so a known reset is durable before it, and a stop between them leaves only the signal, which a resume reads; the legacy writer, which runs only when a run of schemas 1–3 resumes, still appends it after the settlement (`PR380-RESET-LOST-BETWEEN-SETTLEMENT-AND-SIGNAL`, deferred: reordering it there also needs the replay to keep a reviewer's signal past the settlement that retires its pool). A schema-4 run now waits out a known reset at most 5 h 15 min ahead, to two minutes past it, as one deferral (§19); further ahead, or unknown, the ladder still defers three times and then asks a human. A worker's agent with more than one pool may hold a reset already passed: the run waits only to two minutes past it, and after that there is no reset wait, only the ordinary back-off. One pool per agent, and a reviewer's limit, wait only for a reset ahead, as before failover. A reset is spent once its pool refuses again two minutes or more past it, and is neither waited for nor bound on. The retry-at-reset timer above is otherwise not built. On a schema-4 run, a worker's limit now fails over before it waits, when another pool of its agent is not held exhausted (§19).

**Discovery — `upstroke connect`.** Pools are connected, not configured: `connect` scans PATH for official CLIs, checks auth state, detects each plan's quota shape, enumerates available models, and writes the user-level pools file. Tier classification comes from a **capability catalog** shipped with the binary (static data — the no-HTTP invariant holds), with a pragmatic prior for unknowns: providers price their own models, so per-model multipliers and per-token rates rank capability. A model absent from the catalog is never auto-selected — pin it or update. Decision logs later calibrate the catalog with measured pass rates per tier and task kind.

**Credential profiles.** One vendor can back several pools — two Claude Max accounts, say — told apart by each pool's `profile` (§17). A profile is the absolute path of the directory handed to the agent's CLI as its credential location, through the provider's own profile mechanism: an environment variable on the subprocess rather than a token the engine ever handles (invariants 2 and 5). An attempt on a schema-4 run binds the first pool of its agent, in file order, that the run's signals do not hold exhausted. With every one held, it binds the first whose recorded reset is two minutes past, or else the first; a retry that resumes its session keeps that session's pool. `connect` does not enumerate profiles, because no vendor lists them: the operator writes `profile`, and `connect` carries it across a rewrite. A worker runs under the profile of the pool its attempt binds, which the host runner sets as `CLAUDE_CONFIG_DIR`; review and probe processes still use the agent's first pool, whatever is held. A worker's rate limit fails over to another pool of its agent that is not held exhausted (§19). A profile is supported for Claude Code on the host runner only. A profile the run cannot honour, such as a relative path or a missing directory, or one that a set `CLAUDE_CODE_OAUTH_TOKEN` would override, is refused before any agent CLI is started: by a fresh run in `prepare_fresh`, before its lease, and by a resume in its pre-flight, under its locks (§17). Pre-flight then runs the CLI's capability probe under the profile and, for Claude Code alone, its sign-in check (`claude auth status --json`), on a fresh run and on a resume, once under each account Claude Code's pools use, in file order: each profile they name, and the default account when any of them names none or Claude Code has no pool. It stops at the first account that is signed out or whose check fails to answer, and that account refuses the run before it starts or resumes; a CLI that cannot say passes. An agent whose pools use more than sixteen distinct accounts is refused before its sign-in is checked. Other agents' sign-in is not checked at pre-flight, so a signed-out Codex fails at its first attempt (`PR408-CODEX-SIGN-IN-NOT-PREFLIGHTED`). Selecting between several same-kind pools is v0.2 capacity work, and it changes three things: estimates must **attribute** usage per profile rather than aggregate it (local-log parsing reads per-account state, so summing reports one healthy pool where there is one exhausted and one fresh); `reserve` becomes asymmetric, since a plan bought for unattended work has no interactive use to protect; and independent reset windows turn a rate limit from *wait* into *rebind and continue* (§10.5) — the single biggest practical gain for an overnight run. Affinity will still govern the order: prompt caches are per-account, so the binder is to drain one pool toward its reserve and then switch, rather than round-robining and paying cache-cold on every task. Of all this, only failover between pools of the same agent on the same model is built (r6, question 7): the order is file order, no estimate enters the choice, and per-profile attribution, the asymmetric reserve and affinity are not built.

**Strategies** (`routing.strategy.mode`):

- `conserve` — classic cost minimization: route down aggressively, escalate only on failure, defer frontier-hungry tasks toward window resets when a pool is projected to run dry.
- `value-max` — subscription yield management: prepaid capacity that would expire unused has zero marginal cost, so surplus near a reset biases default tiers **up** (spend-down mode) — Opus for implementation, frontier review everywhere — subject to `min`/`max` bounds and the reserve floor. *No shipped tool does this (verified Aug 2026); it is the headline.*
- `deadline` — wall-clock first: maximize parallel throughput within capacity, spilling to API dollars when justified by a configured $/hour ceiling.

The ledger accounts every attempt in both currencies: API-equivalent dollars (honestly labeled — subscription spend is notional) and pool units drained. Where a worker's route reports no spend at all — Copilot's does not (§16) — the total it contributes to is marked `?` rather than presented as complete, since a cross-vendor review makes that the normal case rather than a corner of it. Budgets exist per run ($), per task ($), and per pool (fraction).

**Sequencing:** v0.1 ships the capacity engine **read-only** — the dry-run preview and `upstroke capacity` show each pool's estimated remaining capacity, resets, and what each strategy *would* do. v0.2 wires it into live routing. This de-risks estimator fragility before any routing depends on it, and the preview alone is the demo that sells the product. As built, `upstroke capacity` and `validate` fold the repository's latest run, whatever its schema: its rate-limit signals are held by the same rule a resumed run uses, and its self-metered spend is every settled attempt's and every integration review pass's. A log that cannot be read shows nothing from that run, and the report says so.
