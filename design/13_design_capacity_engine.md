## 13. Capacity engine (P9)

The router's economics depend on which pool pays. Pools have different shapes, and the engine models them explicitly:

| Pool kind | Example | Unit | Reset shape |
|---|---|---|---|
| Subscription windows | Claude Max 5x/20x | tokens (est.) | 5-hour rolling + weekly cap |
| Metered credits | Copilot on AI-Credit billing (post-Jun 2026) | credits ≈ $ | monthly allowance + PAYG |
| Legacy request pools | Copilot annual plans | premium requests × per-model multiplier | monthly |
| API keys | Anthropic/OpenAI direct | dollars | none (budget only) |
| Local | home-server models via an OpenAI-compatible endpoint | unlimited | none (hardware-bound) |

**Estimation sources**, in trust order: (1) rate-limit signals from the CLIs — ground truth; a `RateLimited` outcome immediately marks the pool exhausted, demotes or parks frontier-hungry tasks, and sets a retry-at-reset timer; (2) self-metering of everything the engine spawned; (3) ccusage-style parsing of local agent logs, which captures the user's *interactive* sessions drawing from the same pool; (4) optionally, provider usage endpoints where the provider documents one — asked by the capacity tracker, outside the engine (below), treated as fragile and never load-bearing: a provider's report can lower an estimate and can never raise one. Estimates are always conservative: a per-pool `safety_margin` (usage on other machines is invisible to local log parsing) and a `reserve` floor that keeps headroom for the user's own interactive work.

**Rate limits and resets, as built (2026-11-14).** Source 1 is narrower than the paragraph above reads. Beside a fixed list of phrases (`5-hour limit reached`, `usage limit`, Copilot's credit wording, API errors), a failed attempt is `RateLimited` when its text says it hit a quota window's limit (`You've hit your 5-hour limit`; any number of hours, `session` or `weekly`), or the limit of one of Claude's four model names — Opus, Sonnet, Haiku, Fable — with a reset after it (`You've hit your Fable limit · resets Nov 14, 9am (UTC)`). A model name without a reset, or any other word (`context`, `token`, `request`), is an ordinary task failure. The reset recorded as `pool_exhausted.reset_at`, and carried into `capacity_snapshot`, is read only from the limit's own text: the `resets` that follows the recognised limit on its line, or, when nothing after the limit on its line is a reset, a `resets` that begins the very next line. A reset with no such limit before it — `MCP cache resets 9am (UTC)` alone, or on a later line — is never read, and when the limit's own reset cannot be read (a zone other than UTC, a malformed time) none is recorded and no other reset stands in. Stderr, when that is what signalled the limit, is read before the attempt's reason, and the first of the two that holds a recognised limit decides: the reason is read only when the stderr holds none. Only Claude Code's text is read, since no other vendor's reset format is known, so every other agent records none. The messages give no year, and the short form no date, so the reset is the occurrence nearest the moment the text is read: a limit read a second after its reset keeps that reset, not one a day ahead. A pool gets one `pool_exhausted` per distinct reset. A repeat refusal naming the same reset, or none, writes nothing; the fold, and so a replay or resume, reports the latest signal's reset; a rate-limited deferral with no signal of its own keeps the known reset; and a success retires the pool, reset and all, so the next refusal writes one again. Both engines now record `pool_exhausted` under the same rules. The schema-4 engine appends it before the rate-limited settlement, so a known reset is durable before it, and a stop between them leaves only the signal, which a resume reads; the legacy writer, which runs only when a run of schemas 1–3 resumes, still appends it after the settlement (`PR380-RESET-LOST-BETWEEN-SETTLEMENT-AND-SIGNAL`, deferred: reordering it there also needs the replay to keep a reviewer's signal past the settlement that retires its pool). A schema-4 run now waits out a known reset at most 5 h 15 min ahead, to two minutes past it, as one deferral (§19); further ahead, or unknown, the ladder still defers three times and then asks a human. A worker's agent with more than one pool may hold a reset already passed: the run waits only to two minutes past it, and after that there is no reset wait, only the ordinary back-off. One pool per agent, and a reviewer's limit, wait only for a reset ahead, as before failover. A reset is spent once its pool refuses again two minutes or more past it, and is neither waited for nor bound on. The retry-at-reset timer above is otherwise not built. On a schema-4 run, a worker's limit now fails over before it waits, when another pool of its agent is not held exhausted (§19).

**Machine-level, as built (2026-11-23).** Capacity is tracked for the machine, not for a repository. A subscription is the operator's: two repositories on one machine drain the same window, and a rate limit one of them met is a fact about the pool the other is about to use. So `upstroke capacity` and the `validate` and `--dry-run` preview fold **every run on the machine**, where they folded the latest run of the repository they were started in. Nothing is recorded twice to make that possible: each schema-4 run already keeps its private half under the machine directory (`~/.upstroke/runs/<run-id>/`, §15) with an `owner.json` naming its public directory, which is the index, and each run's `events.jsonl` stays the one record of what it did. A run of schemas 1–3 has no owner record and is found only from inside its own repository. Each log is read by the reader of its own schema: a schema-4 log by the observer `status` reads it with, a stable read of its committed lines and a checked replay, so a log the engine would refuse to resume contributes nothing; a log of schemas 1–3 by the sequential reader. A run is folded once, by its id (since 2026-11-24): a repository copied to a second place with its `.upstroke/` holds a second log of each of its runs, and logs of one id that hold the same events are one run seen twice, folded once with nothing said. Where they differ, the log folded is the one the run's owner record names, else the one holding more events, else the first by path, so the choice never turns on the repository the views were started in; a warning names the run and both logs. A log that cannot be read beside one that can is named the same way, and its run, being folded, is not counted among those that could not be read. The runs' capacity evidence — `pool_exhausted` signals, settled attempts, interrupted attempts, the review passes of a merge verification — is put in one sequence by event time, each run's own order kept exactly, and the rules of one run are applied to it: a signal sets its pool's reset, an attempt the pool served retires it whichever repository ran it, a rate-limited settlement marks its pool and keeps a known reset. Event times are whole seconds, and evidence of one second from different runs is ordered by what it is and by run id, never by the repository the views were started in, so one machine gives one answer wherever it is asked: a refusal waits for another run's success of the same second on its pool, so that success leaves the pool exhausted rather than clearing it, while one run's own refusal and then success in one second still clear it, in that run's order. Only where two runs' refusals and successes of one second cross, each refusing a pool before serving the one the other refused, can no order keep both refusals; the run whose id sorts first then goes first. Self-metered draw counts the current calendar month (UTC), the period `monthly_allowance` is measured against, so a pool's ceiling is its allowance less everything upstroke drew from it on this machine this month, where it was less what one run drew. `[capacity] scope = "repo"` (§17), or `upstroke capacity --scope repo`, folds this repository's runs alone. A run that cannot be read shows nothing: a warning names it, the scope line counts it — with none readable it says the runs found could not be read, never that there are none — and the rest are folded. That is a run none of whose logs either reader accepts, or whose owner record exists and leads to no log, because it cannot be read or parsed, names another run, or names no run directory. A private half with no owner record is a run of schemas 1–3 and is not counted, and neither is the record of a run the repository itself lists, which is read from there. A live run still binds and fails over on its own signals alone (§19): the machine-level fold feeds the read-only views, and making it an input to a run's binding is capacity-driven routing, which is not built. What no fold on this machine can see is unchanged: other machines and the operator's interactive sessions, which is what the margin and the reserve are for.

**The capacity tracker, as built (2026-11-23).** Source 4 needs HTTP, and the engine never speaks it (§4.2). So the asking is done by a separate component, the capacity tracker, which is `upstroke capacity --refresh` and nothing else: for each pool that names a `usage_provider` (§17) it asks that provider's usage endpoint what the account has drawn, and stores the answer under the machine directory, `~/.upstroke/capacity/usage/` (§15). It dispatches no agent, runs no gate, owns no git and writes no event log, and nothing in `run` or `resume` calls it or waits for it; they read the stored reports as files. The direction is the point: a run's behaviour is a function of its event log and the files on disk, and a network answer that arrived or did not arrive mid-run is neither. The split is held mechanically, by the means every other effect boundary here is: the tracker's entry points are on the effect denylist, so a module that states no allowance cannot name them, and a census over every production source file fails if anything but the CLI does.

The request is made by `curl`, as a subprocess, through the Runner — the way upstroke reaches everything else outside itself. The binary links no HTTP client and no TLS stack, and the operator's proxy and certificate settings are `curl`'s to honour. `curl` is given only `https://` addresses fixed in the binary, follows no redirect, reads no `.curlrc`, and is told a time and a size limit; the address and the headers reach it on standard input, so the credential appears in no argument, no environment variable the tracker sets, and no error. An absent `curl` fails the refresh of the pools that needed it, with the lookup's own account, and nothing else.

**Which endpoints.** Only ones their provider documents, taking a credential the provider issues for the purpose. That is invariant 5 applied to HTTP, and it is an admission rule, not a current state: `anthropic-cost` (the Admin API's cost report), `openai-cost` (the organization costs endpoint), `github-ai-credits` and `github-premium-requests` (GitHub's billing usage for Copilot, per account). The widely used subscription-window endpoints are deliberately absent. Claude Code's is undocumented and takes the Claude.ai OAuth credential, which Anthropic's published terms reserve for Claude Code and its own applications; Codex's ChatGPT-plan endpoint and Copilot's internal quota endpoint are likewise not documented public APIs. The clean route to a subscription window's reading is the vendor's own CLI — Claude Code hands its statusline command `rate_limits`, Codex's app server answers `account/rateLimits/read`, the Copilot SDK `account.getQuota` — which is source 3's kind of work, a subprocess and a local read, and not built. Adding a provider is one variant and its two functions, and whether a given endpoint meets the rule is the owner's call (§20).

All four report **spend for the current calendar month**, which is what a billing endpoint knows; none reports what is left. The pool's `monthly_allowance`, in the same units, supplies the other half, and with `"auto"` the report is shown as a note and bounds nothing. A response is untrusted input: each parser reads the fields it needs, and refuses rather than guesses on a currency or a unit it does not expect, a negative or non-finite number, or a page that says more pages follow — each of which would otherwise become a spend figure that is too low, and so a ceiling that is too high. The credential is read from the environment variable the pool names in `usage_token_env`; the tracker reads no agent CLI's credential store, and no credential is ever written to a file. One pool's failure is that pool's line in the output and never ends the refresh, and a failed refresh leaves the report stored before in place.

**What a stored report is worth.** A report is a point-in-time reading, and what makes an old one still worth holding is that usage inside one window only grows: a month with 60 of 100 drawn at noon has at least 60 drawn at one, so "at most 40% left" stays true for as long as the window does not reset. That is the validity rule, and it is why a report's age alone never retires it. A window whose reset has passed says nothing; a window that names no reset is believed for fifteen minutes; a report dated ahead of this machine's clock, or from a provider the pool no longer names, says nothing at all. **A report is bound to the source it was fetched with** (the account since 2026-11-23, the credential's variable since 2026-11-24): usage only grows within one account's window, and a provider that reports per key answers for whichever organization its key belongs to. So every report records the name of the environment variable its credential was read from, which is the pool's `usage_token_env` at the refresh, and, where the provider reports per account, the account it read, which is the pool's `usage_account`. It records names and never a credential, and a provider that reports per key records no account. A report says nothing unless its provider, its variable and, where the provider reads one, its account are each the one the pool names now. A part the report does not record matches nothing, and neither does a part the pool does not name: a report stored before a part was recorded cannot be told apart from another source's, and a pool that names no `usage_token_env`, or no `usage_account` its provider needs, is never refreshed, so no report is about it. A note says which part differs, or that the report predates recording it, and that `upstroke capacity --refresh` replaces the report with one for the source the pool names; for a pool that names no such key, it says the refresh will not run until the pool names one. The variable is matched by its name, so a variable that comes to hold another organization's key under the same name is not detected. Where several windows stand, the tightest binds. In the estimate a report ranks below self-metering, as the trust order above has it, and the rule that follows from "never load-bearing" is that **a provider report only ever sets or lowers a ceiling**: it never raises one a higher-ranked source set, never replaces a rate-limit signal, says nothing about an unmetered pool, and — whatever it reports — never says *exhausted*, which stays a signal's word alone. An estimate it set reads `[provider-reported]`, after the pool's margin and reserve like any other.

**Discovery — `upstroke connect`.** Pools are connected, not configured: `connect` scans PATH for official CLIs, checks auth state, detects each plan's quota shape, enumerates available models, and writes the user-level pools file. Tier classification comes from a **capability catalog** shipped with the binary (static data — the no-HTTP invariant holds), with a pragmatic prior for unknowns: providers price their own models, so per-model multipliers and per-token rates rank capability. A model absent from the catalog is never auto-selected — pin it or update. Decision logs later calibrate the catalog with measured pass rates per tier and task kind.

**Credential profiles.** One vendor can back several pools — two Claude Max accounts, say — told apart by each pool's `profile` (§17). A profile is the absolute path of the directory handed to the agent's CLI as its credential location, through the provider's own profile mechanism: an environment variable on the subprocess rather than a token the engine ever handles (invariants 2 and 5). An attempt on a schema-4 run binds the first pool of its agent, in file order, that the run's signals do not hold exhausted. With every one held, it binds the first whose recorded reset is two minutes past, or else the first; a retry that resumes its session keeps that session's pool. `connect` does not enumerate profiles, because no vendor lists them: the operator writes `profile`, and `connect` carries it across a rewrite. A worker runs under the profile of the pool its attempt binds, which the host runner sets as `CLAUDE_CONFIG_DIR`; review and probe processes still use the agent's first pool, whatever is held. A worker's rate limit fails over to another pool of its agent that is not held exhausted (§19). A profile is supported for Claude Code on the host runner only. A profile the run cannot honour, such as a relative path or a missing directory, or one that a set `CLAUDE_CODE_OAUTH_TOKEN` would override, is refused before any agent CLI is started: by a fresh run in `prepare_fresh`, before its lease, and by a resume in its pre-flight, under its locks (§17). Pre-flight then runs the CLI's capability probe under the profile. It does not check sign-in, so a profile that is not signed in passes pre-flight and fails at its first attempt (`PR386-PROFILE-AUTH-NOT-PREFLIGHTED`). Selecting between several same-kind pools is v0.2 capacity work, and it changes three things: estimates must **attribute** usage per profile rather than aggregate it (local-log parsing reads per-account state, so summing reports one healthy pool where there is one exhausted and one fresh); `reserve` becomes asymmetric, since a plan bought for unattended work has no interactive use to protect; and independent reset windows turn a rate limit from *wait* into *rebind and continue* (§10.5) — the single biggest practical gain for an overnight run. Affinity will still govern the order: prompt caches are per-account, so the binder is to drain one pool toward its reserve and then switch, rather than round-robining and paying cache-cold on every task. Of all this, only failover between pools of the same agent on the same model is built (r6, question 7): the order is file order, no estimate enters the choice, and per-profile attribution, the asymmetric reserve and affinity are not built.

**Strategies** (`routing.strategy.mode`):

- `conserve` — classic cost minimization: route down aggressively, escalate only on failure, defer frontier-hungry tasks toward window resets when a pool is projected to run dry.
- `value-max` — subscription yield management: prepaid capacity that would expire unused has zero marginal cost, so surplus near a reset biases default tiers **up** (spend-down mode) — Opus for implementation, frontier review everywhere — subject to `min`/`max` bounds and the reserve floor. *No shipped tool does this (verified Aug 2026); it is the headline.*
- `deadline` — wall-clock first: maximize parallel throughput within capacity, spilling to API dollars when justified by a configured $/hour ceiling.

The ledger accounts every attempt in both currencies: API-equivalent dollars (honestly labeled — subscription spend is notional) and pool units drained. Where a worker's route reports no spend at all — Copilot's does not (§16) — the total it contributes to is marked `?` rather than presented as complete, since a cross-vendor review makes that the normal case rather than a corner of it. Budgets exist per run ($), per task ($), and per pool (fraction).

**Sequencing:** v0.1 ships the capacity engine **read-only** — the dry-run preview and `upstroke capacity` show each pool's estimated remaining capacity, resets, and what each strategy *would* do. v0.2 wires it into live routing. This de-risks estimator fragility before any routing depends on it, and the preview alone is the demo that sells the product. As built, `upstroke capacity` and `validate` fold every run in scope, whatever its schema — every run on the machine, or this repository's alone (above): rate-limit signals are held by the same rule a resumed run uses, applied across the runs in the order their events happened, and the self-metered spend is every settled attempt's, every interrupted attempt's (unpriced, on the pool it started on) and every integration review pass's, over the current calendar month. A log that cannot be read shows nothing from that run, and the report says so: a warning names the run and the scope line counts it. The machine-level fold and the capacity tracker feed those same read-only views: they change what is estimated and from how much evidence, and nothing binds on either yet.
