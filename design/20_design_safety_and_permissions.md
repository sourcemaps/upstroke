## 20. Safety and permissions

- Unattended agents run with pre-granted, **narrow** permissions materialized per profile (Claude Code settings; Copilot `--allow-tool`; Codex `--sandbox`). The skip-all-permissions class of flags is never used, with one scoped exception decided alongside the v0.2 runner (§21): under a runner that is genuinely external — container-per-attempt — Codex runs its `external-sandbox` mode, because a container kept at standard hardening with the CLI's sandbox stood down beats one granted `SYS_ADMIN` so the inner sandbox can initialise. The exception exists only while the external boundary does. Edit profiles get no network tools; gates are the only commands they may run; reviewers are read-only.
- The engine refuses dirty trees, never force-pushes, never touches remotes.
- `capacity --subscription-usage claude [--auth cli|bearer]` adds an opt-in advisory read (§13). The default CLI route sends at most one bounded `get_usage` control request for windows only, without prompt, model turn, tools, settings or shell, and none when `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_OAUTH_TOKEN` are both set (below). It retains the real `CLAUDE_CONFIG_DIR` and normal CLI auth; Upstroke inspects no credentials and blanks `UPSTROKE_CLAUDE_RESET_TOKEN` in this child. Because a set `CLAUDE_CODE_OAUTH_TOKEN` overrides the selected profile, the route asks only whether that token and `CLAUDE_CONFIG_DIR` are present, never their values: with both present it starts no CLI and reports windows unavailable, naming both variables, with exit 0 and any `--reset-credits claude` grant read unaffected; either alone changes nothing. Windows alone never resolve this token, send HTTP or report a grant status. Adding `--reset-credits claude` independently calls the bearer reset reader once; either report survives the other's failure. Explicit bearer mode uses only the fixed reset GET and dedicated provider-authorized token described below for both windows and grants, with no CLI even when the token is absent. Both flags with bearer auth still use one GET. There is no retry, credential fallback, second GET, native token export or CLI impersonation on HTTP. Windows and grants are independent, safe output only; nothing is stored or redeemed, and these readings never enter pool arithmetic or run/resume.
- The capacity tracker (§13) is the only part of upstroke that makes a network request: a fixed-address HTTPS `GET` or an official CLI usage control request, explicitly requested by `upstroke capacity --refresh`, `upstroke capacity --reset-credits claude` or `upstroke capacity --subscription-usage claude`. The owner may admit known undocumented first-party read-only capacity endpoints: the first is the fixed Claude reset-metadata GET in §13. Credentials must still be explicitly provider-authorized for this integration and supplied by the operator in an environment variable. Admitting an endpoint does not authorize a credential restricted to a vendor's native application: ordinary native-app-only subscription credentials are unsuitable without provider authorization. Reset reads use only `UPSTROKE_CLAUDE_RESET_TOKEN`; they never discover/extract Claude Code credentials, collect or refresh CLI logins, or impersonate the vendor CLI. Missing credentials send no request. The tracker reads no CLI credential store, stores no credential and puts none on a command line. There is no URL input, redirect, POST, redemption or account change. Ordinary capacity/report/run/resume remain non-network paths for the tracker, and Codex stays on the official app-server `account/rateLimits/read`. Billing refreshes store spend figures under the machine directory; reset inventory is advisory and not persisted.
- Plans are data, but an agent executing a malicious plan step with edit rights is not: trust in the plan's source is a prerequisite. For untrusted plans, run in a container or dedicated user; the engine never elevates.
- Before public launch: re-verify each provider's terms on headless/automated CLI use. This includes two specifics the design deliberately leaves to that check. **Multi-account pooling** (§13): profiles the operator holds and pays for is a different question from pooling accounts across people, which is account sharing and out of scope whatever the answer. **Spend-down** (§13's `value-max`): using prepaid capacity is not a violation, but a strategy whose stated purpose is to consume quota before it expires sits close to the usage pattern rate limits exist to shape — which is why `conserve` is the derived default and spend-down is opt-in. In both cases the mechanism is the vendor's own sanctioned surface, so an unfavourable answer costs a config option rather than an architecture. The official-CLI-only stance is the defensible posture; keep it clean.
