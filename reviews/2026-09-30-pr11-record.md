### R-A — production effect none, and the legacy engine

**Packet.** `sequential_substrate.runner`: "Runner::run(&RunnerRequest) -> ProcessOutput
synchronous until PR11 (then a boxed Send future)". `design/08_design_trait_surface.md:50-56`:
"every async trait used behind `dyn` returns a boxed `Send` future … The pre-Tokio runner steps use
the same request/output contract through a synchronous `run`; step 5 changes that call shape to
the boxed-future surface while parity tests hold process and parsing semantics fixed". PR11's
`production_effect` is none; schemas 1–3 always run the legacy engine
(`sequential_substrate.selection`).

**Code.** §2's caller list: the legacy engine, the adapters' `probe`/`discover`, the gates and the
reviews call `run` synchronously and consume its `Result` on the spot.

**Reading.** `Runner::run` becomes
`fn run<'a>(&'a self, request: &'a RunnerRequest, call: RunnerCall<'a>) -> RunFuture<'a>`, with
`RunFuture<'a> = Pin<Box<dyn Future<Output = Result<ProcessOutput, RunnerError>> + Send + 'a>>`:
the request stays one borrowed value, the trait stays object-safe behind the same `&dyn Runner`,
and what travels with the call (`RunnerCall`: the cancellation token and optional per-invocation
observers, R-I) is a second argument rather than a field of the request. **Every synchronous
caller meets it through one blocking adapter**, `Runner::run_blocking` (and `run_blocking_with`
for a caller that carries a call), provided methods that drive the future to completion on the

**How parity is proved.** (1) The whole existing suite, green, over the migrated call sites — the

**Alternatives.** Keep a synchronous `run` and add an asynchronous `run_async` beside it —

### R-E — where the concurrency seam is cut

**Packet.** `single_writer`: "one coordinator owns EventLog and every ref mutation";
`design/26_design_merge_queue_protocol.md:210-213`: "Only the coordinator owns `EventLog` and Git
ref mutation. Tokio workers return typed results over channels." `completion_identity`:
"verification completions carry (sequence, candidate)". The merge module is frozen (R-D).

**Code.** §2: attempts run in `attempt.rs` (worker, capture, gates through `run_registered`,
reviews through the `ReviewPasses` seam), settle in `settle.rs`/`run.rs`, promote in
`candidate.rs` — none frozen. Integration runs in `integrate.rs` — frozen — as one synchronous
chain from `merge_verification_started` through `journal.verify(..)` to the terminal append and
the CAS (`integrate.rs:672-806`), reached through two seams the coordinator implements:
`IntegrationJournal` (append, fold, hooks, `converted`) and `Verification` (`verify`, `ids`).

**Reading.** *Attempts* are lifted by restructuring the unfrozen substrate: an attempt pipeline
(worker, capture, gates, reviews) runs on a blocking thread and returns a typed completion bound to
`(key, generation, attempt)`; every append (`attempt_started`, `attempt_finished`,
`candidate_prepared`, `task_candidate_created`) and every ref mutation (the candidate-prepared
pin, the candidates ref) stay on the coordinator. *Integration verification* is lifted **at the
`Verification` seam**: the coordinator runs `integrate()` itself, so every append and the CAS stay
on its thread, and its `verify` hands the gates and reviews to a verification pipeline and **keeps
the coordinator loop running while it waits** — processing other pipelines' completions, slot
grants and dispatches — until the pipeline's typed completion for `(sequence, candidate)` arrives,
then returns it to `integrate.rs`, which appends the terminal exactly as today. The seam's
signature already allows it: `verify(&mut self, ..)` holds the whole coordinator, and
`integrate()` holds nothing across the call that another append could invalidate (it re-reads
`journal.fold()` after `verify` returns). A halt, shutdown or append error that arrives while the
verification is in flight cancels the pipeline and makes `verify` return an error, so
`integrate.rs` appends nothing further and the closure (phase 4) settles the verification with
`merge_verification_interrupted`. **Consequences phases 3 and 4 inherit:** a cancelled Runner
error must never be classified as an outage — today `IntegrationCx::verify` maps fate `Gone` to an
infrastructure outage (`run.rs:151-170`) and a review pass reports a `Gone` Runner error as the
review being unavailable (`src/review.rs:547-560`), both of which a cancellation would reach, so the
cancellation is typed (`RunnerError::is_cancelled`, phase 1) and those arms test it first; and `integrate.rs`'s
private reclaim helpers are not reachable from `closure.rs`, so the live closure reclaims staging,
snapshots and the prepared pin through `WorkspaceManager`'s funnels, as recovery does.

**Alternatives.** (a) Split `start_and_verify` at `journal.verify` so the coordinator can resume a
transaction when the pipeline returns — an edit to a frozen file, the owner's to allow. (b) Run
`integrate()` on a pipeline thread behind a journal proxy — rejected: the pin and the CAS
(`publish`) would be ref mutations off the coordinator, against `single_writer`. (c) Block the
coordinator for the verification's duration — rejected: no dispatch, halt or append-error handling
while it waits, and a deadlock the first time a reviewer waits for a slot only the blocked
coordinator can grant (INV-18: "atomic slot pairs granted by the coordinator loop"). The re-entrant
loop is the one option that keeps the merge module byte-identical, the coordinator the single
writer, and INV-18's never-block; it is phase 3's to build and phase 3's review to hold.

### R-F — "the coordinator never awaits"

**Packet.** INV-18: "The coordinator never blocks on an entitlement, provisional reservation, or
slot"; `deadlock_freedom`: "entitlements are never awaited; provisional reservations are taken
only when the derived count permits and are converted or cancelled without waiting".

**Reading.** What awaits: **pipelines** — a pipeline awaits its slot pair (a pending request the
coordinator grants from the head-reservation FIFO when both slots are free) and awaits its Runner
completion (the Runner's future, driven on the pipeline's blocking thread). What never awaits: the
**coordinator** — entitlements are fold-derived counts compared, never waited on; a provisional
reservation is taken only when the count permits and is converted at its first append or
cancelled; a slot grant is a decision in the coordinator loop, never a wait; the coordinator never
polls a Runner future (a host or container future does its supervision inside the poll, R-I, so
polling one would block the coordinator for the life of a process). The coordinator's only wait is
for its next message — a completion or a request — including inside R-E's verification seam.

### R-I — where the Runner's future does its work

**Code.** The Unix reaper takes its shared cleanup-lease holds on the run directories the
*spawning thread* has entered (`rundir::active_cleanup_lease_paths`, a `thread_local!`,

**Reading.** The host and container runners' futures run their whole supervision — environment,
program resolution, spawn, supervision loop, reap — in the poll that first sees them, on the
polling thread. A Runner future is therefore driven from a thread that may block: the blocking

### R-L — "FIFO with head reservation", defined

**Packet.** `permits.protocol`: "if slotted, wait for the atomic pair grant (FIFO with head
reservation)"; `deadlock_freedom`: "head reservation prevents slot starvation";
`alternatives[74]`: "strict head-of-line FIFO for slots — rejected: blocks disjoint work; head
reservation adopted".

**Reading.** Waiting requests form one queue in arrival order. The **head** — the oldest waiting
request — reserves every slot it waits for: one slot of its agent and, when it has a pool, one of
its pool. A request is granted when (a) it is the head and its pair fits the free capacity
(`held + 1 <= limit` for its agent and its pool), or (b) it is behind the head and its pair fits the
capacity left **after the head's reservation** (`held + 1 + 1 <= limit` on a resource the head also
needs, `held + 1 <= limit` on any other). So a later request is **backfilled** past a waiting head
only when it takes nothing the head waits for. The grant procedure after every registration,
completion and cancellation: grant heads while they fit, then backfill the rest in arrival order
against the new head's reservation; cancelling the head moves the reservation to the next request
(`permits.protocol`'s "head reservation recomputed"), which can grant requests the old head held
back. Shutdown and the append-error protocol withdraw every waiting request together, granting
nothing on the way.

**Why the head cannot starve.** While a request is the head no grant can take a slot it reserved,
so every holder of a resource it is blocked on was granted before it became the head; holders are
running processes that wait for nothing and end, so the head is granted at the first release that
frees its last blocking slot, and every later request becomes the head in turn.
`permits::tests::seeded_adversarial_orders_grant_every_request_in_order_and_exceed_no_limit`
checks that invariant after every step of 256 seeded adversarial orders.

**Alternatives.** Strict FIFO — the packet's rejected one. Backfill with no reservation — a head
needing two slots that free at different times loses the first to every later request that fits
it, which is the starvation the reservation exists to prevent
(`identity::tests::a_waiting_head_reserves_every_slot_it_needs_so_no_later_request_starves_it`).
Reserving for every waiting request rather than the head only — equivalent to strict FIFO on any
shared resource.

### R-M — the selection identity of a provisional reservation

**Packet.** `permits.provisional_reservations`: "process-lifetime bridge between a selection
decision and its first append … conversion at the append; cancellation on any pre-append failure,
run end, shutdown, or a poisoned fold … the sequential substrate asserts at most one" — so above
width 1 several may be outstanding. The G6 matrix: "provisional reservation — owner: selection
interval (dispatch, retry, integration); uniqueness: one per selected task or candidate". INV-18:
"every … provisional conversion is bound to a unique InvocationId or selection identity". ST-02:
"duplicate complete/cancel/release for an InvocationId or provisional reservation is ignored and
counted".

**Reading.** A reservation is bound to `(TaskKey, ReservationKind)`, at most one outstanding per
task. One per task is structural, not a convention: a task can be selected for exactly one of the
three admissions at a time — dispatch requires no open generation and no queued candidate, retry a
retained-idle generation, integration a queued candidate, and the queue holds at most one candidate
per task — and a second reservation for a task with one outstanding is refused
(`Reservations::reserve`). The key identifies a candidate as well, which is what the frozen
`IntegrationJournal::converted(key)` converts by. **Staleness.** Every conversion is made by the
coordinator at the append it bridges and every pre-append cancellation at the failure, in the same
step, so an operation from an earlier interval of the same `(task, kind)` cannot arrive after a
later one began. A conversion or cancellation naming a reservation that was taken and is no longer
outstanding is a duplicate or a stale operation: ignored and counted (ST-02). One naming a
reservation never taken, or naming the task's outstanding one under another kind, is refused.

**Alternative.** Bind to `(task, generation, attempt)` or `(sequence, candidate)` — the frozen

### R-N — the acquisition order as an API rule, and where the fold is read

**Packet.** `deadlock_freedom`: "acquisition order pipeline -> merge -> {agent, pool} (atomic

**Reading.** The order is a precondition of the slotted registration, not a convention:
`InvocationLedger::register_slotted` takes a `Standing`, read from the fold for the pipeline the

### R-R — the threading model: a plain-thread coordinator, pipelines on the blocking pool

**Packet.** `design/26_design_merge_queue_protocol.md:210-213`: "Only the coordinator owns
`EventLog` and Git ref mutation. Tokio workers return typed results over channels."
`tests_acceptance.determinism`: "seeded scheduling permutations under Tokio".

**Code.** The Runner's future does its whole supervision in its first poll (R-I), so whatever
polls it blocks for the life of the process; `integrate()` calls `Verification::verify`
synchronously (`integrate.rs:696`). Measured on Tokio 1.53.1 by the memo's probe (memo §3.1,
`~/orch-pr11/logs/pr11_research_c/tokio-blocking-probe.log`): `UnboundedReceiver::blocking_recv`
works on a plain thread, on a `spawn_blocking` thread and nested inside a synchronous call from
its own receive loop, and panics only inside `Runtime::block_on` or a worker task.

**Reading (memo §3, model M1).** The coordinator is the caller's own thread — the one that calls
`TopologyRun::step` at width 1 — and never runs inside a runtime context: it waits only in
`blocking_recv` on its inbox, in its main loop and inside `verify` (R-V). Each pipeline runs on the
runtime's blocking pool (`spawn_blocking`) and drives its Runner futures there with
`run_blocking_with` (R-I), waiting for coordinator replies (a slot grant, a snapshot grant) on
`oneshot` receivers. The runtime is built per coordinator, multi-thread with one worker thread (no
task is ever spawned onto it), its blocking pool bounded by the run's `max_parallel`, and every
pool thread named after the calling thread, because the observation export keys its record on
the current thread's name (`src/observations.rs:156-157`). Tokio moves to `[dependencies]`, still
`=1.53.1`, `default-features = false`, features `rt`, `rt-multi-thread` and `sync` — no `process`,
`fs`, `net`, `signal`, `io-*`, `macros` or `time` (R-C). A pipeline's body runs under
`catch_unwind`, so a panicking pipeline sends a defined completion (an error) rather than leaving
the coordinator waiting on an inbox nothing will write, and every pipeline's `JoinHandle` is
joined before the entry returns (standards §10).

**Alternatives.** (M2) the coordinator as an async task inside `block_on`: `verify` is synchronous
and called from the frozen `integrate()`, so it could wait only through `block_in_place`, which
panics on a current-thread runtime, and every other synchronous wait would need the same wrapping.
(M3) pipelines on `std::thread::scope`: no `'static` cost, but Tokio would shrink to its channels,
against "Tokio workers" (memo §3.2).

### R-S — the cut: what the coordinator keeps and what a pipeline runs

**Packet.** `single_writer`: "one coordinator owns EventLog and every ref mutation";
`completion_identity`: "attempt-level completions carry (key, generation, attempt); verification
completions carry (sequence, candidate); slot grants/releases/cancels and invocation registrations

**Code.** `TopologyRun::step` (`run.rs:691-746`) runs one branch to completion: the dispatch

assessment, the review inputs and the judgement (`run.rs:1318-1417`), then the settlement or the

**Reading (memo §2.1–2.2).** Every append and every ref mutation stays in the function that makes
it today, on the coordinator. A pipeline is exactly a span between two appends of one identity:
the **attempt body** `run_worker → capture → candidate_diff → assess → inputs → judge` (between
`attempt_started` and `attempt_finished`/`candidate_prepared`), and the **verification body**
(today's `judge_proposal`, between `merge_verification_started` and the transaction's terminal).
`dispatch()` — the reservation, `task_dispatched`, the intent, the worktree add and a repair's
materialization — and `attempt_started` stay on the coordinator, so the fold never shows a
generation `OpenNoAttempt` while a pipeline is creating its worktree, and `eligible_continuation`
cannot select a generation that is live (memo §2.1). The hand-backs are `Judged(key, generation,
attempt)` and `Verified(sequence, candidate)`, each carrying the body's typed result, and the
per-invocation `Admit`/`Ended` of R-U, bound to `InvocationId`; R-W adds the snapshot gate's two.
The coordinator's only waits are its inbox and the synchronous work it already did at width 1
(its own Git, filesystem and appends).

**Alternative.** Create the worktree inside the pipeline — rejected: the fold would show the
generation `OpenNoAttempt` until a later hand-back, and selection would dispatch it a second time
unless a process-local mask shadowed `eligible_continuation`.

### R-U — the broker client: one registration path for `step` and for pipelines

**Packet.** `permits.protocol`: "register(invocation_id, slots) -> if slotted, wait for the atomic
pair grant (FIFO with head reservation) else immediately runnable -> … -> complete(invocation_id)
releasing any slots … or cancel(invocation_id) …"; INV-18: "atomic slot pairs granted by the
coordinator loop".

**Code.** The judge registers the worker and each gate through `register_now` and settles through
the ledger it borrows (`attempt.rs:939-990`); a review pass reaches its pair through
`preflight::Registering` over a `Mutex` of the same ledger (`attempt.rs:839-871`,
`preflight.rs:168-275`); the synchronous substrate refuses a pair it cannot be granted at once

invocation's pipeline.

**Reading (memo §2.2 H3, §10.4).** One trait — the registrar — is the only way an invocation of an
attempt or a verification is registered and settled: `admit` (register; for a slotted invocation,
take its atomic pair) and `ended` (complete or cancel). Two implementations. **Inline**, for `step`,
the pre-flight and run creation: the evolved ledger behind a `Mutex`, registering at once and
refusing with INV-18's sentence exactly as today (R-O). **Channel**, for a spawned pipeline: `admit`
sends `Admit{pipeline, invocation, pair}` and waits on a `oneshot` for the grant — the pipeline
waits, never the coordinator — and `ended` sends `Ended`. The coordinator processes `Admit` by
reading the pipeline's `Standing` from the fold at that moment (R-N) and registering in the
broker; a grant is replied at once or when a later `complete`/`cancel` returns it (phase 2's
`complete`/`cancel` return the requests they newly grant). `preflight::Registering` becomes
generic over the registrar, so the review pass's count check (R-P) keeps its guarantee under both.
Every Runner call a pipeline makes carries the pipeline's `Cancellation` and the cleanup-lease
paths of R-Z, injected where the call is built (the judge's own calls) or rebuilt (the decorator
around a review pass), so the coordinator can cancel a pipeline's process from its own thread
(R-I). A pipeline runs its invocations one after another, so it holds at most one at a time.

**Alternative.** A second, channel-only decorator beside `Registering` — rejected: two
implementations of register/slot/run/settle, which is what R-P removed.

### R-AA — completions and identity

**Packet.** `completion_identity` (quoted in R-S): "a completion applies only if its identity is the

**Reading (memo §6).** Before any append a completion passes, in order: (1) a poisoned fold —
discard; (2) a `PipelineId` not in the live table — discard, warn, count; (3) an identity other than
the table's — discard, warn, count; (4) an entry marked cancelled — discard and count; (5) the fold

### R-AB — pipeline errors, idle-only arms, the overshoot bound, and cancellation is never an outage

**Reading (disposition 9; memo §5, §6, R4–R6).**
- **A pipeline that returns an error** (a Runner error the body does not settle, a Git error in the
  capture or the judgement, a refused registration) ends the command as `step`'s `Err` does at
  width 1: the coordinator cancels every other pipeline, waits for each to terminate, discards what
  they return, and ends the command resumably; no `attempt_interrupted` is appended live
  ("permitted_transitions: none new"); the next resume settles the open attempts interrupted. A
  coordinator-side error (a settlement's Git failure, a refused dispatch) ends it the same way. A
  panicking pipeline is an error of the same kind (R-R).
- **Backoff, hard block and closure are taken only when no pipeline is live**, by the same
  functions `step` runs; with pipelines live, those arms mean "wait for the next message". The cost
  is latency: a deferred item waits for the in-flight pipelines; `defer_wait_elapsed` is never placed
  among in-flight settlements.
- **The budget overshoot bound** is the unknown spend of at most `max_parallel` live pipelines, each
  running one invocation at a time: `select` checks the ceiling against settled spend only. It is
  stated in the notes and, from phase 4, the report text — never in a durable field ("durable_events:
  none new").
- **A cancelled Runner error is never classified as an outage**: the width-1 verification mapping
  and `review::run_review`'s review-unavailable mapping (`src/review.rs:549`) test
  `RunnerError::is_cancelled` first and return the error. The legacy path never cancels, so its
  behaviour is unchanged.

### R-AC — a run ending with pipelines live, in phase 3

**Reading (disposition 10; closure under concurrency is phase 4's).** Phase 3 handles an ending run
minimally: admission stops. A **halt** (a halting settlement appended while other pipelines are
live) cancels every live pipeline and waits for each to terminate, discarding what it returns; a
**budget stop** drains — the live pipelines settle naturally (the fold accepts their settlements
while ending, memo §4.2) — and admits nothing. When nothing is live the closure runs as at width 1.
If it would need closure steps (2)–(4) — an in-flight attempt, a promoting generation, an unresolved
transaction, which is what a halt's cancellation leaves — `closure::refuse_unclosable`'s refusal
stands, nothing is appended, and the command ends resumably; phase 4 replaces that refusal. A halt
inside `verify` leaves the transaction `VerificationStarted` for the same refusal.

### R-AD — deterministic intake and the quiescence observer

**Packet.** `tests_acceptance.determinism`: "deterministic sequential scheduler; seeded scheduling
permutations under Tokio; no sleeps".

**Reading (memo §8).** The coordinator tracks, for every live pipeline, whether it is running on
its own, waiting for a coordinator reply, inside a granted invocation, or finished. `PipelineSeams`
may carry a quiescence observer (a test seam; production installs none). With none, messages are
processed as they arrive. With one, the coordinator buffers what arrives and processes it only when
no pipeline is running on its own, in a canonical order (by `PipelineId`, then message kind), and
when nothing is buffered it hands the observer the granted invocations — the scheduler completes one
of them in the test runner, chosen by its seed — or lets it inject a forged or recorded message
(ST-01, ST-02, ST-06). So a seed reproduces the same run, and a stuck run (quiescent, nothing to
release) is an error rather than a hang. The test runner records per-invocation results (keyed by
the request), and `durable_at_spawn` parses complete lines only, since the coordinator may be
mid-append when a pipeline's process starts.

## 11. What is not claimed

- Nothing of phases 3–7: no coordinator, no concurrency above width 1 anywhere in production or in
  the substrate; `closure::refuse_unclosable` still refuses. No production path cancels an
  invocation yet: cancellation is exercised by tests only.
- **Phase 2's broker waits for nothing and nobody waits on it yet.** There is no coordinator loop
  handing grants to waiting pipelines (phase 3): at width 1 every slotted request is made on the
  coordinator's own thread and must be granted at once or is refused (R-O). Queued requests, grants
  on release and the head reservation are exercised by broker-only tests; **no runtime pool test**
  (a real multi-thread Tokio runtime driving pipelines that await grants) exists yet — acceptance
  item 3's runtime half and G6's "runtime pool tests" are phase 6's, which re-runs the slot tests and
  the seeded orders under the runtime.
- The configured `max_per_agent`/`max_per_pool` are not wired to any schema-4 run: no caller holds a
  `Config` there yet, so `TopologyRun` uses the packet's default, the recorded `max_parallel`
  (R-K). Phase 3's coordinator passes the configured limits.
- A pre-flight agent probe's pair is `{agent, none}`: the pre-flight holds no pool table. The probes
  run one at a time before admission, so no pool contention is possible there at this width.
- A judgement's standing is read once, when the judge is built: sound at width 1, where nothing is
  appended while a judgement runs. Phase 3, which moves judgements onto pipeline threads while the
  coordinator appends, has to read it at the coordinator for each registration.
- `PR7-R3-ATTEMPT-002`'s finding file is not deleted in this phase (§6).
- No mutation campaign was run for phase 2. The broker's oracles are structural where they can be:
  held counts are derived from the holders rather than stored, a pair is released only by settling
  the registration that holds it, and the seeded test checks the head-reservation invariant after
  every step rather than a final state.
- The Windows and macOS behaviour of the new code is compiled, not run, on this box (§8, §10).
- Cancellation's latency is the supervision loop's tick (50 ms on the host, the configured poll on
  the container runner) plus the termination; the host test bounds the whole at under 60 seconds
  against a 300-second child and does not measure the tick.
- A Runner future of the host or container runner cannot be dropped mid-flight — its supervision is
  inside one poll — so "dropping an in-flight invocation terminates it" is carried by the token for
  those runners; drop-while-held is exercised on the test double only.

  structural: `a_runner_level_observer_still_takes_invocations_one_at_a_time` is the concurrency
  test's oracle failing under a shared observer lock (the pre-PR11 shape), and the cancellation
