### R-A — production effect none, and the legacy engine

**Packet.** `sequential_substrate.runner`: "Runner::run(&RunnerRequest) -> ProcessOutput
synchronous until PR11 (then a boxed Send future)". `design/08_design_trait_surface.md:50-56`:
"every async trait used behind `dyn` returns a boxed `Send` future … The pre-Tokio runner steps use
the same request/output contract through a synchronous `run`; step 5 changes that call shape to
the boxed-future surface while parity tests hold process and parsing semantics fixed". PR11's
`production_effect` is none; schemas 1–3 always run the legacy engine
(`sequential_substrate.selection`).

**Code.** §2's caller list: the legacy engine, the adapters' `probe`/`discover`, the gates and the
reviews call `run` synchronously and consume its `Result` on the spot.

**Reading.** `Runner::run` becomes
`fn run<'a>(&'a self, request: &'a RunnerRequest, call: RunnerCall<'a>) -> RunFuture<'a>`, with
`RunFuture<'a> = Pin<Box<dyn Future<Output = Result<ProcessOutput, RunnerError>> + Send + 'a>>`:
the request stays one borrowed value, the trait stays object-safe behind the same `&dyn Runner`,
and what travels with the call (`RunnerCall`: the cancellation token and optional per-invocation
observers, R-I) is a second argument rather than a field of the request. **Every synchronous
caller meets it through one blocking adapter**, `Runner::run_blocking` (and `run_blocking_with`
for a caller that carries a call), provided methods that drive the future to completion on the
calling thread with a thread-park waker — no Tokio runtime on the legacy path. The host and
container runners' futures do their whole supervision in the poll that first sees them (R-I), so
on the legacy path the process is spawned, supervised and reaped on the same thread, with the same
environment composition, program resolution, hooks, output and errors as before. The adapters'
`probe` and `discover` stay synchronous and call `run_blocking`: design §8 also writes `async fn
probe`, but PR11's scope names the Runner's surface only, and an async adapter surface is not
needed by anything PR11 builds.

**How parity is proved.** (1) The whole existing suite, green, over the migrated call sites — the
suite already holds process and parsing semantics fixed (`runner::host::tests::supervision_parity_tests`
runs the Runner against the direct funnel over the parity fixtures;
`runner::contract::tests::adapter_parse_parity` drives every adapter's parser through a
`&dyn Runner`; the role-grid and environment-composition tests pin what each role's child
receives). (2) New parity tests for the adapter itself: that `run_blocking` drives the host
runner's future on the calling thread (the child is created from the caller's thread, so the
thread-scoped state of §2 is the caller's), and that a call that was never cancelled reports what
the direct funnel reports. (3) No schema-1..3 path changes behaviour: the migration of each call
site is the mechanical `run(` → `run_blocking(` and nothing else, and every test double that
answered `run` synchronously keeps its body and implements the test-only
`contract::tests::InlineRunner` instead (a blanket impl gives it the future); §5's tier-2 check holds
exactly that for the frozen modules' tests.

**Alternatives.** Keep a synchronous `run` and add an asynchronous `run_async` beside it —
rejected: it contradicts the packet's literal "Runner::run … then a boxed Send future" and the
notes' promise that PR11 turns `run` into the future "behind this same `dyn`"
(`docs/internals/runner/contract.md`, "`fn the_runner_trait_is_object_safe()`"). A Tokio runtime
per legacy call — rejected: a runtime per invocation, a panic when a caller is already inside a
runtime, and a Tokio dependency on the legacy path. A private `block_on` at each caller —
rejected: N copies of one executor.

### R-B — no new effect primitive

### R-E — where the concurrency seam is cut

**Packet.** `single_writer`: "one coordinator owns EventLog and every ref mutation";
`design/26_design_merge_queue_protocol.md:210-213`: "Only the coordinator owns `EventLog` and Git
ref mutation. Tokio workers return typed results over channels." `completion_identity`:
"verification completions carry (sequence, candidate)". The merge module is frozen (R-D).

**Code.** §2: attempts run in `attempt.rs` (worker, capture, gates through `run_registered`,
reviews through the `ReviewPasses` seam), settle in `settle.rs`/`run.rs`, promote in
`candidate.rs` — none frozen. Integration runs in `integrate.rs` — frozen — as one synchronous
chain from `merge_verification_started` through `journal.verify(..)` to the terminal append and
the CAS (`integrate.rs:672-806`), reached through two seams the coordinator implements:
`IntegrationJournal` (append, fold, hooks, `converted`) and `Verification` (`verify`, `ids`).

**Reading.** *Attempts* are lifted by restructuring the unfrozen substrate: an attempt pipeline
(worker, capture, gates, reviews) runs on a blocking thread and returns a typed completion bound to
`(key, generation, attempt)`; every append (`attempt_started`, `attempt_finished`,
`candidate_prepared`, `task_candidate_created`) and every ref mutation (the candidate-prepared
pin, the candidates ref) stay on the coordinator. *Integration verification* is lifted **at the
`Verification` seam**: the coordinator runs `integrate()` itself, so every append and the CAS stay
on its thread, and its `verify` hands the gates and reviews to a verification pipeline and **keeps
the coordinator loop running while it waits** — processing other pipelines' completions, slot
grants and dispatches — until the pipeline's typed completion for `(sequence, candidate)` arrives,
then returns it to `integrate.rs`, which appends the terminal exactly as today. The seam's
signature already allows it: `verify(&mut self, ..)` holds the whole coordinator, and
`integrate()` holds nothing across the call that another append could invalidate (it re-reads
`journal.fold()` after `verify` returns). A halt, shutdown or append error that arrives while the
verification is in flight cancels the pipeline and makes `verify` return an error, so
`integrate.rs` appends nothing further and the closure (phase 4) settles the verification with
`merge_verification_interrupted`. **Consequences phases 3 and 4 inherit:** a cancelled Runner
error must never be classified as an outage — today `IntegrationCx::verify` maps fate `Gone` to an
infrastructure outage (`run.rs:151-170`) and a review pass reports a `Gone` Runner error as the
review being unavailable (`src/review.rs:547-560`), both of which a cancellation would reach, so the
cancellation is typed (`RunnerError::is_cancelled`, phase 1) and those arms test it first; and `integrate.rs`'s
private reclaim helpers are not reachable from `closure.rs`, so the live closure reclaims staging,
snapshots and the prepared pin through `WorkspaceManager`'s funnels, as recovery does.

**Alternatives.** (a) Split `start_and_verify` at `journal.verify` so the coordinator can resume a
transaction when the pipeline returns — an edit to a frozen file, the owner's to allow. (b) Run
`integrate()` on a pipeline thread behind a journal proxy — rejected: the pin and the CAS
(`publish`) would be ref mutations off the coordinator, against `single_writer`. (c) Block the
coordinator for the verification's duration — rejected: no dispatch, halt or append-error handling
while it waits, and a deadlock the first time a reviewer waits for a slot only the blocked
coordinator can grant (INV-18: "atomic slot pairs granted by the coordinator loop"). The re-entrant
loop is the one option that keeps the merge module byte-identical, the coordinator the single
writer, and INV-18's never-block; it is phase 3's to build and phase 3's review to hold.

### R-F — "the coordinator never awaits"

**Packet.** INV-18: "The coordinator never blocks on an entitlement, provisional reservation, or
slot"; `deadlock_freedom`: "entitlements are never awaited; provisional reservations are taken
only when the derived count permits and are converted or cancelled without waiting".

**Reading.** What awaits: **pipelines** — a pipeline awaits its slot pair (a pending request the
coordinator grants from the head-reservation FIFO when both slots are free) and awaits its Runner
completion (the Runner's future, driven on the pipeline's blocking thread). What never awaits: the
**coordinator** — entitlements are fold-derived counts compared, never waited on; a provisional
reservation is taken only when the count permits and is converted at its first append or
cancelled; a slot grant is a decision in the coordinator loop, never a wait; the coordinator never
polls a Runner future (a host or container future does its supervision inside the poll, R-I, so
polling one would block the coordinator for the life of a process). The coordinator's only wait is
for its next message — a completion or a request — including inside R-E's verification seam.

### R-I — where the Runner's future does its work

**Code.** The Unix reaper takes its shared cleanup-lease holds on the run directories the
*spawning thread* has entered (`rundir::active_cleanup_lease_paths`, a `thread_local!`,
`src/rundir/cleanup/scopes.rs:28-29`, read at `src/agent/proc.rs:2466`), and the substrate enters
the run's scope on the thread that steps the loop (`run.rs:696`); the observation export attributes
a record to the current thread's name (`src/observations.rs:156-157`).

**Reading.** The host and container runners' futures run their whole supervision — environment,
program resolution, spawn, supervision loop, reap — in the poll that first sees them, on the
polling thread. A Runner future is therefore driven from a thread that may block: the blocking
adapter's caller today, a pipeline's blocking thread in phase 3 (which cannot enter the run's
cleanup scope, a thread-local the coordinator's thread holds, and carries the scope's lease paths
into every call instead — R-Z). That is the explicit blocking boundary §10 of the standards asks
for, and it keeps R28's hold and the observation attribution exactly where they are. The
cancellation carried with the call is observed by the supervision loop (host) and the container
supervision loop, so a cancel from another thread terminates the tree through the existing
terminate path and the future then resolves as cancelled with fate `Gone` (`NeverStarted` when
the call was cancelled before anything started). A future dropped before its first poll started
nothing; a future of these two runners cannot be dropped mid-flight, because its supervision is
inside one poll — so the protocol's "cancelled after the Runner terminated its process" is carried
by the token, and the broker (phase 2) releases an invocation once, when its future reports.

**Alternative.** Offload the supervision to a thread the runner spawns and make the future a
receiver. Rejected for phase 1: the reaper would take no lease on the run directory (the offload
thread entered no scope) unless the scope were propagated into the reaper's arming — a change to
R28's machinery that belongs with R28 under concurrency (phase 5), not with the call shape — and
every test that observes spawn points would see them on another thread. Nothing in phases 2–6
needs the offload: pipelines are blocking-thread code anyway (capture and snapshots are Git
subprocesses and filesystem work).

### R-L — "FIFO with head reservation", defined

**Packet.** `permits.protocol`: "if slotted, wait for the atomic pair grant (FIFO with head
reservation)"; `deadlock_freedom`: "head reservation prevents slot starvation";
`alternatives[74]`: "strict head-of-line FIFO for slots — rejected: blocks disjoint work; head
reservation adopted".

**Reading.** Waiting requests form one queue in arrival order. The **head** — the oldest waiting
request — reserves every slot it waits for: one slot of its agent and, when it has a pool, one of
its pool. A request is granted when (a) it is the head and its pair fits the free capacity
(`held + 1 <= limit` for its agent and its pool), or (b) it is behind the head and its pair fits the
capacity left **after the head's reservation** (`held + 1 + 1 <= limit` on a resource the head also
needs, `held + 1 <= limit` on any other). So a later request is **backfilled** past a waiting head
only when it takes nothing the head waits for. The grant procedure after every registration,
completion and cancellation: grant heads while they fit, then backfill the rest in arrival order
against the new head's reservation; cancelling the head moves the reservation to the next request
(`permits.protocol`'s "head reservation recomputed"), which can grant requests the old head held
back. Shutdown and the append-error protocol withdraw every waiting request together, granting
nothing on the way.

**Why the head cannot starve.** While a request is the head no grant can take a slot it reserved,
so every holder of a resource it is blocked on was granted before it became the head; holders are
running processes that wait for nothing and end, so the head is granted at the first release that
frees its last blocking slot, and every later request becomes the head in turn.
`permits::tests::seeded_adversarial_orders_grant_every_request_in_order_and_exceed_no_limit`
checks that invariant after every step of 256 seeded adversarial orders.

**Alternatives.** Strict FIFO — the packet's rejected one. Backfill with no reservation — a head
needing two slots that free at different times loses the first to every later request that fits
it, which is the starvation the reservation exists to prevent
(`identity::tests::a_waiting_head_reserves_every_slot_it_needs_so_no_later_request_starves_it`).
Reserving for every waiting request rather than the head only — equivalent to strict FIFO on any
shared resource.

### R-M — the selection identity of a provisional reservation

**Packet.** `permits.provisional_reservations`: "process-lifetime bridge between a selection
decision and its first append … conversion at the append; cancellation on any pre-append failure,
run end, shutdown, or a poisoned fold … the sequential substrate asserts at most one" — so above
width 1 several may be outstanding. The G6 matrix: "provisional reservation — owner: selection
interval (dispatch, retry, integration); uniqueness: one per selected task or candidate". INV-18:
"every … provisional conversion is bound to a unique InvocationId or selection identity". ST-02:
"duplicate complete/cancel/release for an InvocationId or provisional reservation is ignored and
counted".

**Reading.** A reservation is bound to `(TaskKey, ReservationKind)`, at most one outstanding per
task. One per task is structural, not a convention: a task can be selected for exactly one of the
three admissions at a time — dispatch requires no open generation and no queued candidate, retry a
retained-idle generation, integration a queued candidate, and the queue holds at most one candidate
per task — and a second reservation for a task with one outstanding is refused
(`Reservations::reserve`). The key identifies a candidate as well, which is what the frozen
`IntegrationJournal::converted(key)` converts by. **Staleness.** Every conversion is made by the
coordinator at the append it bridges and every pre-append cancellation at the failure, in the same
step, so an operation from an earlier interval of the same `(task, kind)` cannot arrive after a
later one began. A conversion or cancellation naming a reservation that was taken and is no longer
outstanding is a duplicate or a stale operation: ignored and counted (ST-02). One naming a
reservation never taken, or naming the task's outstanding one under another kind, is refused.

**Alternative.** Bind to `(task, generation, attempt)` or `(sequence, candidate)` — the frozen
`converted(key)` carries only the key, and a sequence is not allocated until the append the
reservation bridges.

### R-N — the acquisition order as an API rule, and where the fold is read

**Packet.** `deadlock_freedom`: "acquisition order pipeline -> merge -> {agent, pool} (atomic
pair); slot holders are running processes that wait for nothing; entitlements are never awaited;
provisional reservations are taken only when the derived count permits … therefore no hold-and-wait
cycle". INV-18: "acquisition order pipeline -> merge -> {agent, pool} is acyclic".

**Reading.** The order is a precondition of the slotted registration, not a convention:
`InvocationLedger::register_slotted` takes a `Standing`, read from the fold for the pipeline the
invocation belongs to, and refuses a pair to a pipeline the fold shows holding nothing. An attempt
stands when its generation is `InFlight` with that attempt number (its processes run between
`attempt_started` and its settlement; an earlier attempt's identity is stale, INV-20); a sequence
stands when the fold's open transaction is that sequence and its verification has started; a
pre-flight probe always stands (probes run before admission and hold no entitlement); a poisoned
fold admits nothing. With entitlements never awaited (a refused reservation is an error, not a
wait) and holders waiting for nothing, no process holds a slot while waiting for an entitlement,
and none holds an entitlement while waiting for anything but a slot: no hold-and-wait cycle.

**Where the fold is read.** `events::log::tests::the_stable_prefix_barrier_is_the_only_way_a_log_becomes_a_topology_fold`

naming `TopologyFold` are exactly a listed 21. The first cut of this phase named it in four more
(`permits.rs`, `attempt.rs`, `preflight.rs`, `dispatch.rs`) and the census failed
(`~/orch-pr11/logs/pr11_impl_b/dev/suite-1/test.log`). Rather than edit a frozen test, the fold
readers — `Entitlements::of` (R1, R2) and `Standing::of` — live in `src/engine/topology/select.rs`,

judge and the registering boundary take their results as values, and the emitter seam grows

### R-R — the threading model: a plain-thread coordinator, pipelines on the blocking pool

**Packet.** `design/26_design_merge_queue_protocol.md:210-213`: "Only the coordinator owns
`EventLog` and Git ref mutation. Tokio workers return typed results over channels."
`tests_acceptance.determinism`: "seeded scheduling permutations under Tokio".

**Code.** The Runner's future does its whole supervision in its first poll (R-I), so whatever
polls it blocks for the life of the process; `integrate()` calls `Verification::verify`
synchronously (`integrate.rs:696`). Measured on Tokio 1.53.1 by the memo's probe (memo §3.1,
`~/orch-pr11/logs/pr11_research_c/tokio-blocking-probe.log`): `UnboundedReceiver::blocking_recv`
works on a plain thread, on a `spawn_blocking` thread and nested inside a synchronous call from
its own receive loop, and panics only inside `Runtime::block_on` or a worker task.

**Reading (memo §3, model M1).** The coordinator is the caller's own thread — the one that calls
`TopologyRun::step` at width 1 — and never runs inside a runtime context: it waits only in
`blocking_recv` on its inbox, in its main loop and inside `verify` (R-V). Each pipeline runs on the
runtime's blocking pool (`spawn_blocking`) and drives its Runner futures there with
`run_blocking_with` (R-I), waiting for coordinator replies (a slot grant, a snapshot grant) on
`oneshot` receivers. The runtime is built per coordinator, multi-thread with one worker thread (no
task is ever spawned onto it), its blocking pool bounded by the run's `max_parallel`, and every
pool thread named after the calling thread, because the observation export keys its record on
the current thread's name (`src/observations.rs:156-157`). Tokio moves to `[dependencies]`, still
`=1.53.1`, `default-features = false`, features `rt`, `rt-multi-thread` and `sync` — no `process`,
`fs`, `net`, `signal`, `io-*`, `macros` or `time` (R-C). A pipeline's body runs under
`catch_unwind`, so a panicking pipeline sends a defined completion (an error) rather than leaving
the coordinator waiting on an inbox nothing will write, and every pipeline's `JoinHandle` is
joined before the entry returns (standards §10).

**Alternatives.** (M2) the coordinator as an async task inside `block_on`: `verify` is synchronous
and called from the frozen `integrate()`, so it could wait only through `block_in_place`, which
panics on a current-thread runtime, and every other synchronous wait would need the same wrapping.
(M3) pipelines on `std::thread::scope`: no `'static` cost, but Tokio would shrink to its channels,
against "Tokio workers" (memo §3.2).

### R-S — the cut: what the coordinator keeps and what a pipeline runs

**Packet.** `single_writer`: "one coordinator owns EventLog and every ref mutation";
`completion_identity`: "attempt-level completions carry (key, generation, attempt); verification
completions carry (sequence, candidate); slot grants/releases/cancels and invocation registrations
carry InvocationId"; `permits.protocol`: "a pipeline holds at most one invocation at a time".

**Code.** `TopologyRun::step` (`run.rs:691-746`) runs one branch to completion: the dispatch
(`dispatch.rs:130-177`), `attempt_started`, the worker, capture, the candidate diff, the
assessment, the review inputs and the judgement (`run.rs:1318-1417`), then the settlement or the
promotion (`run.rs:1419-1580`); an integration runs the frozen `integrate()`, whose stale arm calls
`verify` between `merge_verification_started` and its terminal (`integrate.rs:672-806`).

**Reading (memo §2.1–2.2).** Every append and every ref mutation stays in the function that makes
it today, on the coordinator. A pipeline is exactly a span between two appends of one identity:
the **attempt body** `run_worker → capture → candidate_diff → assess → inputs → judge` (between
`attempt_started` and `attempt_finished`/`candidate_prepared`), and the **verification body**
(today's `judge_proposal`, between `merge_verification_started` and the transaction's terminal).
`dispatch()` — the reservation, `task_dispatched`, the intent, the worktree add and a repair's
materialization — and `attempt_started` stay on the coordinator, so the fold never shows a
generation `OpenNoAttempt` while a pipeline is creating its worktree, and `eligible_continuation`
cannot select a generation that is live (memo §2.1). The hand-backs are `Judged(key, generation,
attempt)` and `Verified(sequence, candidate)`, each carrying the body's typed result, and the
per-invocation `Admit`/`Ended` of R-U, bound to `InvocationId`; R-W adds the snapshot gate's two.
The coordinator's only waits are its inbox and the synchronous work it already did at width 1
(its own Git, filesystem and appends).

**Alternative.** Create the worktree inside the pipeline — rejected: the fold would show the
generation `OpenNoAttempt` until a later hand-back, and selection would dispatch it a second time
unless a process-local mask shadowed `eligible_continuation`.

### R-U — the broker client: one registration path for `step` and for pipelines

**Packet.** `permits.protocol`: "register(invocation_id, slots) -> if slotted, wait for the atomic
pair grant (FIFO with head reservation) else immediately runnable -> … -> complete(invocation_id)
releasing any slots … or cancel(invocation_id) …"; INV-18: "atomic slot pairs granted by the
coordinator loop".

**Code.** The judge registers the worker and each gate through `register_now` and settles through
the ledger it borrows (`attempt.rs:939-990`); a review pass reaches its pair through
`preflight::Registering` over a `Mutex` of the same ledger (`attempt.rs:839-871`,
`preflight.rs:168-275`); the synchronous substrate refuses a pair it cannot be granted at once
(R-O). R-N's rule: a slotted registration presents a `Standing` read from the fold for the
invocation's pipeline.

**Reading (memo §2.2 H3, §10.4).** One trait — the registrar — is the only way an invocation of an
attempt or a verification is registered and settled: `admit` (register; for a slotted invocation,
take its atomic pair) and `ended` (complete or cancel). Two implementations. **Inline**, for `step`,
the pre-flight and run creation: the evolved ledger behind a `Mutex`, registering at once and
refusing with INV-18's sentence exactly as today (R-O). **Channel**, for a spawned pipeline: `admit`
sends `Admit{pipeline, invocation, pair}` and waits on a `oneshot` for the grant — the pipeline
waits, never the coordinator — and `ended` sends `Ended`. The coordinator processes `Admit` by
reading the pipeline's `Standing` from the fold at that moment (R-N) and registering in the
broker; a grant is replied at once or when a later `complete`/`cancel` returns it (phase 2's
`complete`/`cancel` return the requests they newly grant). `preflight::Registering` becomes
generic over the registrar, so the review pass's count check (R-P) keeps its guarantee under both.
Every Runner call a pipeline makes carries the pipeline's `Cancellation` and the cleanup-lease
paths of R-Z, injected where the call is built (the judge's own calls) or rebuilt (the decorator
around a review pass), so the coordinator can cancel a pipeline's process from its own thread
(R-I). A pipeline runs its invocations one after another, so it holds at most one at a time.

**Alternative.** A second, channel-only decorator beside `Registering` — rejected: two
implementations of register/slot/run/settle, which is what R-P removed.

**Corrected in round R2 (§13).** "A grant is replied at once or when a later `complete`/`cancel`
returns it" held for the grant and not for its recipient: the reply went to whichever pipeline waited
for it, without asking whether that pipeline still served an identity the fold holds open. The
standing is read once, at registration — a gate registers with none — so a pair freed later could go
to a pipeline whose identity a decline had closed since: stopping one closed pipeline granted the next
(review round 2's `R2-RECONCILE-GRANT`). As repaired, every place a grant is delivered asks the fold
first, and a grant for a pipeline that is cancelled or serves a closed identity is withdrawn
undelivered and its request refused.

### R-AA — completions and identity

**Packet.** `completion_identity` (quoted in R-S): "a completion applies only if its identity is the
current open one; otherwise discarded with a non-durable warning; duplicates refused (INV-20); no
completion is applied after the fold is poisoned by an append error". INV-20's enforcement:
"identity check in the coordinator loop before any append".

**Reading (memo §6).** Before any append a completion passes, in order: (1) a poisoned fold —
discard; (2) a `PipelineId` not in the live table — discard, warn, count; (3) an identity other than
the table's — discard, warn, count; (4) an entry marked cancelled — discard and count; (5) the fold
check — an attempt's generation must be `InFlight` with that attempt number, a verification's must
be the open transaction's started verification of that sequence and candidate, read through

entry is removed and the completion applied. A stale settlement that reached the fold would fail
`plan_transition` and end the command (`emit.rs:237-240`), so the check is the coordinator's, and
the fold's refusal stays the replay-side guard. Warnings join `TopologyRun::warnings`; a discard
counter sits beside them. An `Ended` or `Admit` naming an invocation that is not the sending
pipeline's is discarded and counted; a duplicate `Ended` of the pipeline's own invocation reaches
the ledger, which ignores and counts it (phase 2). The tests' injector (R-AD) is checked like a
pipeline and is never trusted as one: an injected completion, end or request is refused and
counted, and settles or releases nothing.

### R-AB — pipeline errors, idle-only arms, the overshoot bound, and cancellation is never an outage

**Reading (disposition 9; memo §5, §6, R4–R6).**
- **A pipeline that returns an error** (a Runner error the body does not settle, a Git error in the
  capture or the judgement, a refused registration) ends the command as `step`'s `Err` does at
  width 1: the coordinator cancels every other pipeline, waits for each to terminate, discards what
  they return, and ends the command resumably; no `attempt_interrupted` is appended live
  ("permitted_transitions: none new"); the next resume settles the open attempts interrupted. A
  coordinator-side error (a settlement's Git failure, a refused dispatch) ends it the same way. A
  panicking pipeline is an error of the same kind (R-R).
- **Backoff, hard block and closure are taken only when no pipeline is live**, by the same
  functions `step` runs; with pipelines live, those arms mean "wait for the next message". The cost
  is latency: a deferred item waits for the in-flight pipelines; `defer_wait_elapsed` is never placed
  among in-flight settlements.
- **The budget overshoot bound** is the unknown spend of at most `max_parallel` live pipelines, each
  running one invocation at a time: `select` checks the ceiling against settled spend only. It is
  stated in the notes and, from phase 4, the report text — never in a durable field ("durable_events:
  none new").
- **A cancelled Runner error is never classified as an outage**: the width-1 verification mapping
  and `review::run_review`'s review-unavailable mapping (`src/review.rs:549`) test
  `RunnerError::is_cancelled` first and return the error. The legacy path never cancels, so its
  behaviour is unchanged.

**Corrected in round R1 (§13).** Two claims above held for attempts and not for everything a pipeline
ends with. *Pipeline errors:* a verification's error completion was held until the snapshot drain
before it ended anything (the early review's `R1-CONC-2`); as repaired, every fatal completion — a
caught panic included — is classified as it is received and interrupts at once, inside `verify` as
outside, before anything the pipeline held is retired or granted on. *Release:* "waits for each to
terminate" was true of the pipelines and not of their invocations — an invocation that ended with its
process unresolved, or was never reported ended, was released by the ledger and its pair granted on
(`R1-CONC-1`). As repaired, such an invocation keeps its registration and pair for the rest of the
process, and is itself an interrupt; the command ends under this reading's error path.

### R-AC — a run ending with pipelines live, in phase 3

**Reading (disposition 10; closure under concurrency is phase 4's).** Phase 3 handles an ending run
minimally: admission stops. A **halt** (a halting settlement appended while other pipelines are
live) cancels every live pipeline and waits for each to terminate, discarding what it returns; a
**budget stop** drains — the live pipelines settle naturally (the fold accepts their settlements
while ending, memo §4.2) — and admits nothing. When nothing is live the closure runs as at width 1.
If it would need closure steps (2)–(4) — an in-flight attempt, a promoting generation, an unresolved
transaction, which is what a halt's cancellation leaves — `closure::refuse_unclosable`'s refusal
stands, nothing is appended, and the command ends resumably; phase 4 replaces that refusal. A halt
inside `verify` leaves the transaction `VerificationStarted` for the same refusal.

### R-AD — deterministic intake and the quiescence observer

**Packet.** `tests_acceptance.determinism`: "deterministic sequential scheduler; seeded scheduling
permutations under Tokio; no sleeps".

**Reading (memo §8).** The coordinator tracks, for every live pipeline, whether it is running on
its own, waiting for a coordinator reply, inside a granted invocation, or finished.
`run_concurrently` takes an optional quiescence observer (a test seam; production passes none).
With none, messages are processed as they arrive. With one, the coordinator buffers what arrives
and processes it only when no pipeline is running on its own, in a canonical order (by

when nothing is buffered it hands the observer the granted invocations — the scheduler completes one
of them in the test runner, chosen by its seed — or lets it inject a forged or recorded message
(ST-01, ST-02, ST-06). So a seed reproduces the same run (true only as repaired in round C1; see
the correction below), and a stuck run (quiescent, nothing to release) is an error rather than a
hang. The test runner records per-invocation results (keyed by
the request), and `durable_at_spawn` parses complete lines only, since the coordinator may be
mid-append when a pipeline's process starts.

**Corrected in round C1 (§13): as built at `aea75a79` this reading claimed more than the code
delivered.** The coordinator marked a pipeline `Invoking` when it *sent* the grant. A pipeline
between its grant and its Runner call was therefore running on its own while the coordinator
applied the next message, appended, cancelled, or asked the observer. "No pipeline is running on
its own" was false for it, and a seed did not reproduce the run. Three things could vary: which
granted calls a cancellation found started, the order processes started in, and the log each saw at
its start. The first two are measured (§13); the third is read from the code. The order in which
the coordinator applied messages did not vary. CI met it on all three test legs. **The reading as
repaired:** under an observer, every grant is handed to it at once
(`Quiescence::granted`, from `started`), and the coordinator does nothing else until the observer
returns. The observer returns when the invocation is inside the Runner, which only the test's runner
can see. So every invocation `Invoking` names is inside the Runner whenever the coordinator acts.
The test scheduler makes that checkable: its runner starts no call until the scheduler admits it,
and at every quiescent point the scheduler asserts that each granted invocation is inside. A seed
now reproduces the invocations released, the processes started and their order, the log each saw at
its start, and the canonical log (`one_seed_reproduces_one_run_down_to_what_each_process_saw_when_it_started`).
Not reproduced: the order in which one interrupt's simultaneous cancellations are recorded by the
double, which is unordered.

**A further correction, round R1 (§13).** On cancellation the coordinator marked every live pipeline
`Running`, including one `Awaiting` whose request was still in the intake's buffer, unapplied; the
intake then waited on the inbox for a pipeline that was waiting on the intake, for ever — a halt ingested
in the pass after a pipeline's end whose next request was buffered behind it hung the command
(`a_halt_answers_a_request_its_intake_still_buffers`, red at `898e7338` by its watchdog). As repaired, a
cancelled pipeline inside an invocation is `Running`, and one waiting for a reply only once its reply is
refused; a buffered request is answered when the intake applies it. Production has no buffer.

### R-AE — a granted invocation cancelled before its process starts (round C1)

**Packet.** `cancellation`: "shutdown or halt cancels pending requests, cancels/releases granted and
non-slotted invocations after termination (processes and containers)"; `permits.protocol`:
"… complete(invocation_id) releasing any slots … or cancel(invocation_id) …".

**Code.** A cancellation that lands between a grant and the pipeline's Runner call reaches the
Runner as an already-cancelled call. The host runner starts nothing and reports
`RunnerError::cancelled(.., NeverStarted)` (`a_call_cancelled_before_it_starts_spawns_nothing`), and
so did the test double. The pipeline reports `Ended{completed: false}` after the call returns
(`attempt.rs`, `execute_typed`; `preflight.rs`, `Registering::settle`), and the coordinator cancels
the registration in the ledger once (`end_invocation`). The double recorded **no ending** for such a
call: no `Ran`, nothing in `endings()`.

**Reading.** A granted invocation cancelled before its process starts **is cancelled and released
once**. It is cancelled, because its call returns a cancellation and no process runs. It is released
once, as a cancellation, by its pipeline's end report after the call returned — "after
termination", where nothing had to be terminated. The ledger shows it cancelled, not completed and
not twice. The test double therefore records it, as `Ending::CancelledBeforeStart`, distinct from
`Cancelled` (started, then terminated), so an oracle can tell whether a process ran.
`RecordingRunner::ran` still lists only processes that started. Under the deterministic intake as
repaired (R-AD) the coordinator never produces this position by itself. Production's arrival-order
intake can, and a test reaches it with the double's barred door (`RecordingRunner::bar`):
`a_shutdown_releases_each_invocation_once_whether_pending_unstarted_running_or_finished`.

**Alternative.** Leave the double silent and count cancellations through the ledger only. Rejected:
an oracle reading the double's endings is then blind to exactly the cancellations that race a
grant. That blindness is what let phase 3's shutdown test encode a thread-timing assumption.

### R-AF — closure step (2) under concurrency: what is settled interrupted, and by whom

**Packet.** `closure_procedure` (2): "Halted -> cancel every in-flight attempt and verification (Runner
terminates processes/containers; attempt_interrupted per in-flight attempt;
merge_verification_interrupted per in-flight verification with prepared pin deleted expected-old and
snapshots reclaimed)"; T-ATTEMPT: "at Halted the same terminal is appended by cancellation", its
`resume_action` naming the residue ("snapshot intents and worktrees reclaimed … the task worktree
scrubbed with force"); T-VERIFY: "Halted cancellation appends the interrupted terminal".

**Code.** Phase 3's `Coordinator::halt` (`coordinator.rs:1258`) cancels every live pipeline and
`finish` (`:1301`) drains them before `TopologyRun::close_run` (`run.rs:1445`), which refuses what the
cancellation left (`closure::refuse_unclosable`, `closure.rs:37`, R-AC). Recovery performs the same
terminals on recovery typestate only: `recover::settle_interrupted` (`recover.rs:1401`) and
`finish_integration` (`:1096`) take `&mut PreflightCertified`, and `integrate.rs`'s own reclaim
helpers are private (`:1017`, `:1030`). `closure::refuse_unclosable` and `closure::unclosable` are
pinned by the frozen `recover/tests.rs`
(`closure_refuses_an_in_flight_generation_and_an_unresolved_transaction_before_any_append`: an
in-flight attempt and a started verification each refused, "PR11" and "nothing was appended" in the
text).

**Reading.** The closure settles interrupted **exactly the in-flight identities whose pipelines this
process's coordinator cancelled and saw end** — never an identity it cannot vouch for. The
coordinator records each identity when it cancels its pipeline (`cancel_all`), and the sequence of a
verification it abandons inside `verify` (whose completion may already have arrived and been
discarded); `finish` hands that set to the closure only after every pipeline has ended, so every
process behind it has been terminated by the Runner and every invocation released by its own
pipeline's end report (R-AE). **An identity is vouched only when its pipeline's end established
termination.** A cancelled pipeline's completion is read before it is discarded: when its error carries
`ProcessFate::Unresolved` — the Runner could not establish that the process or container is gone — the
identity is not vouched, the closure is not entered, and the command ends resumably naming the
invocation, so no terminal is appended and no worktree scrubbed over a process that may still run; the
next process's census reclaims the container and its recovery settles the identity. This is phase 4's
side of the early review's `R1-CONC-1` (`~/orch-pr11/reviews/early-review-R1-triage.md`: `Ended` discards
the fate, so the ledger releases an unresolved invocation's pair), whose repair in phase 3's protocol is
round R1's; phase 4 builds nothing on that release, and after an interrupt nothing is granted to anyone
(pending requests withdrawn, every reply refused, every `Admit` refused). *Round R1 (§13):* `Ended` now
carries the fate, an unresolved invocation keeps its registration and pair, and the unresolved fates the
closure reads come from the ends themselves, for cancelled and uncancelled pipelines alike. *Round R2
(§13):* a verification whose result had arrived when the halt was recorded is vouched too — `verify`
records its sequence for every interrupt, and the halt now reaches it (`R2-CONC4-1`); its pipeline had
ended, and each of its invocations had reported an end that established its process gone, or the
command would have ended on the unresolved one. `close_run` takes the set: an
in-flight attempt or started verification
outside it is refused with PR10's wording kept ("… PR11 … nothing was appended"); the width-1 loop and
the coordinator's idle closure pass an empty set, so for them PR10's refusal stands unchanged — the
synchronous loop never leaves an attempt or a verification in flight, and a fresh process's recovery
settles a dead coordinator's before the loop runs. A non-empty set outside a Halted ending is refused
too: a budget stop drains, it never cancels. For each vouched identity, in key order and then the
verification (recovery's (d) before (f)): `attempt_interrupted` (lease by kind,
`GenerationLease::expected(false)`, as recovery writes it), then the attempt's residue — the snapshots
its own names produce (`JudgeNames::Attempt{..}.owns`, the scope R-Y gave `discard_residue`) and the
task worktree scrubbed (`dispatch::scrub`); `merge_verification_interrupted`, then the pin deleted
expected-old (`integrate::prune_pin`, public), the staging worktree and intent removed
(`integrate::staging_slot`, public), and **this sequence's** snapshots only
(`JudgeNames::Integration{sequence}.owns`: `s<seq>-integration`, `s<seq>-review<n>`). Every effect

pin, staging, snapshots); none of the frozen files is edited.

**Alternatives.** (a) Call `recover::settle_interrupted`/`finish_integration` — they take recovery's
typestate, which a live run does not have. (b) Append `attempt_interrupted` for every in-flight

snapshot intent (recovery's `reclaim_snapshot_residue`) — at width > 1 an unscoped reclaim is the
defect R-W exists to avoid; the attempts' own discards already cover theirs.

### R-AG — closure steps (3) and (4) at a live run end

**Packet.** (3) "Promoting generations: complete promotion (candidates ref if absent,

### R-AH — the budget stop under concurrency: `budget_exceeded` first, the drain, and its end

**Packet.** `precedence_consequences`: "the coordinator checks the ceiling before every dispatch, retry,
or integration selection and … appends budget_exceeded before any effect … halt outranks budget: after
budget_exceeded is recorded, a drained in-flight settlement that is halting makes derived_outcome
Halted, remaining in-flight work is cancelled as for Halted, and run_finished(BudgetExceeded) is
refused"; (2) "BudgetExceeded -> drain to natural settlements, and if any drained settlement is halting
the closure continues as Halted from step (2)"; (5b) deferred items never block Halted or
BudgetExceeded.

**Reading.** Every admission pass — outside `verify` and inside it — selects through `admitted()`,
whose ceiling check turns a breach into `budget_exceeded` before anything the admission would have
done, **against spend that is current**: a verification's review records are charged to the run's
spend when its completion is accepted, before the next admission pass, not when `verify` returns after
the snapshot drain (phase 4's side of the early review's `R1-CONC-4`; R-V's own sentence, "charged when
its completion arrives", as it now holds); the run then ends for budget only through the closure, which reads budget only from the durable
stop (`ending_outcome`). **The drain:** while ending, admission and answer ingestion stop (`admit`
returns at `run_is_ending`; `ingest_answers` reads nothing while ending), slot and snapshot grants go on
so live pipelines can finish, and their completions are settled as at any time (the fold accepts
settlements while ending). **Its end condition:** no pipeline is live — every live pipeline has sent its
completion and been retired; inside `verify`, the verification's own completion has arrived and no
attempt snapshot is live (R-W) — after which the next idle pass selects the closure. **The halting
conversion:** a halting settlement drained while other pipelines are live makes the next admission pass
cancel them (the halt interrupt), so the closure runs as Halted from step (2) with them vouched
(R-AF); drained last, it leaves nothing live and the closure reads Halted, since `ending_outcome` reads
halt before budget. `run_finished(BudgetExceeded)` is never attempted after it, and the fold refuses
it (`check_run_finished`). **What this build can drain:** a halting settlement is, live, only a
declined answer (`question_answered` with `decline_halts_run`) — the ladder's terminal failure that
halts (`Next::Fail`: `NoChain`, or no rungs) is never produced on the schema-4 path, where exhaustion
asks a person — and the fold refuses `question_answered` while a budget stop is current
(`check_question_answered`), which is also why ingestion stops. So no halting settlement can be drained
live after `budget_exceeded` at any width: the conversion is the admission pass's halt check, the one a
halt with pipelines live takes (`halt_cancels_in_flight_attempt_at_width_three`), and the closure's
precedence over a halting drain settlement is asserted on a width-three prefix that plants one
(`run_finished_budget_exceeded_refused_after_halting_drain_settlement_at_width_three`). The overshoot bound of R-AB is
unchanged and stays in the notes: the report is `deny_unknown_fields` and carries no width, and a new
report field is a report-schema change this slice does not make (§11).

**Every interrupt cancels at receipt.** A halt, a shutdown and an append error each cancel every live
pipeline in the same coordinator step that records the interrupt (`cancel_all` from `halt`, from the
`Shutdown` message's handling and from `fail`), inside `verify` as outside it; `verify` then returns
without waiting for the snapshot drain. The early review's `R1-CONC-2` (a *fatal verification
completion* held in `verify` until the drain) is a different receipt, repaired by round R1 (§13): a
fatal completion now interrupts as it is received.

**Corrected in round R2 (§13).** The admission pass acted on a recorded halt only while a pipeline was
live (`halted && !live.is_empty()`), so "drained last, it leaves nothing live" also covered the
verification `verify` still held — its result accepted, its pipeline retired, its transaction open —
and that verification was then prepared and published after the halt (review round 2's
`R2-CONC4-1`). As repaired, the pass reads the fold's in-flight work too: the halt interrupts the
verification, and the closure settles it with `merge_verification_interrupted`. A budget stop is
unchanged: it drains, and an arrived verification reaches its natural terminal.

### R-AI — an append error under concurrency

**Packet.** `append_error_protocol`: the event is outcome-unknown, the fold is poisoned, the append is
never retried, no report, status, question payload or cleanup is derived from the poisoned fold, the log
is reopened and the stable-prefix barrier established, the command ends naming present, absent or
undetermined, "in-flight invocations are cancelled through the Runner (PR11: pipelines cancelled;
completions discarded)"; the slice contract: "a returned append error cancels in-flight pipelines and

**Code.** Every coordinator append goes through `TopologyRun`'s emitting paths, which run the protocol
(`emit.rs:264`: poison, the provisional reservation cancelled, the barrier, the report) and discharge its
obligation (3) at once (`EmitFailure::discharging`, `emit.rs:315` → `UncancelledAppend::cancelling`,
`:159` → `InvocationLedger::cancel_all_running`, `identity.rs:867`), then return the report as the

them, and `check` discards every completion of a poisoned fold (R-AA).

**Reading.** That is the protocol under concurrency, and phase 4 changes none of it; it tests it with
pipelines in flight at each error-return shape. The ledger half of obligation (3) is discharged at the
protocol, as at width 1: each running registration is settled cancelled there, and the pipelines are
cancelled through the Runner by `fail` at once; each pipeline's own end report after its process
terminated is then a counted duplicate that releases nothing (R4: "ignored and counted"). Nothing can
be granted between the two — the fold is poisoned (every standing reads `Holds::Nothing`), the interrupt
refuses every `Admit`, and the pending requests were withdrawn by the same settlement. No closure,
report, status or cleanup follows: `finish` returns the protocol's error, whose text is the report. The
next process follows the surviving prefix through its own barrier (recovery unchanged).

shutdown and halt) by deferring the discharge — obligation (3) is discharged inside every emitting call
site (`run.rs`, `attempt.rs`, `dispatch`, recovery's frozen emitter), and deferring it means a second
discharge path through all of them; the early release is observable only as the duplicate count, and it
can grant nothing.

### R-AJ — shutdown: how it is requested, what it cancels

**Packet.** `cancellation`: "shutdown or halt cancels pending requests, cancels/releases granted and
non-slotted invocations after termination (processes and containers), cancels provisional reservations,
discards completions … resume performs the recovery order … coordinator ledgers empty at restart".

**Reading.** A shutdown is `ToCoordinator::Shutdown` on the coordinator's inbox. In PR11 only a test
sends it (the injector); production has no caller of `run_concurrently` (R-G), and PR12 wires the
command's signal handling to the same message — no handler is added now (Tokio's `signal` feature stays
off, R-C, and nothing in the packet needs one before activation). On it the coordinator cancels every
live pipeline, withdraws every pending request (so no head remains to reserve for), refuses every reply
still owed, drains every pipeline (each running invocation released by its own end report after its
process terminated, R-AE), discards every completion, cancels any provisional reservation (none can be
outstanding when a message is applied — each is converted or cancelled within the coordinator step that
took it — so one found is warned about), appends nothing, and ends the command resumably. The next

### R-AK — an error or a kill inside the closure

**Packet.** `closure_procedure`: "an append error anywhere in this procedure ends the command under the
append-error protocol and the next process repeats the closure from the surviving prefix"; T-FINISH
`kill_inside_closure_recovers`, `append_error_inside_closure_ends_command_and_resume_completes_closure`.

**Reading.** Each closure append propagates (`self.emit(..)?`), so an append error there ends the
command under the protocol like any other. The next process repeats the closure from what survived:
its recovery settles the remaining in-flight identities interrupted (d), closes retained generations
(e), completes promotions and publications (f), recreates open generations (g), and appends
`run_resumed`; `halted_at` is never cleared, so its loop selects the closure at once and appends
`run_finished(Halted)`. Under a budget stop, `run_resumed` clears the epoch's stop, so the resumed run
continues (a raised budget) rather than re-ending — the packet's resumable BudgetExceeded.

### R-AL — a width-3 run that a real resume can follow (tests only)

**Code.** The scaffold's `Wide` fixture (phase 3) writes its log beside a private directory that is not
`<root>/runs/<run id>`, records a run id its manager does not carry, and writes no owner or commit
record, so the frozen recovery order cannot resume it.

**Reading.** Phase 4's resume claims (shutdown, append error, closure error and kill, the budget stop's
deferred items) are made by resuming through the frozen `recover::run_recovery_order` itself, over a
width-3 run laid out as run creation lays one out: `Wide::durable` in `scaffold.rs` (test-only) writes
the log at the public directory's `events.jsonl`, the private half at `<root>/runs/<run id>` with its

process's locks and hands the directory to the recovery order with test seams (a fake container

#### `R1-REG-1` — a removal's hooks deadlock on the registry lock

**The finding** (regression lens, verbatim in part): "`remove_worktree_proving` holds the new registry mutex
across `funnel`, including its `Before` and `After` callbacks. A callback calling `worktree_records()` attempts to
acquire that same non-reentrant mutex. … At head `83a387bd`, execution stopped inside the `Before` callback until
the three-second watchdog terminated it. … It also contradicts R-X's assertion that the lock is never nested and
its holder waits only for Git or filesystem operations."

**The witness**, `workspace_manager::tests::an_observer_lists_the_worktrees_from_both_hooks_of_a_removal`: a task
worktree removed through `remove_worktree` with an observer whose hook lists the worktrees at `Before` and
`After`; the removal runs on its own thread and is waited for 60 s, so the regression fails rather than hangs the
suite. **Red at `898e7338`**: "the removal did not return within 60s" (`repro/final-dc3136fb/an_observer_lists_the_worktrees_from_both_hooks_of_a_removal.log`).
**Green at `dc3136fb`**: the `Before` hook lists two worktrees and the `After` hook one, as the reviewer saw at the

**The root cause.** Phase 3's lock (R-X) wrapped the whole removal, and `funnel` calls the observer inside it; the
holder therefore waited for whatever the observer did, and a registry reader in the observer took the same lock
on the same thread. Phase 4 adds no holder; its closure removes worktrees through this funnel, so the deadlock was
reachable from its reclaim too.

**The repair: the lock is released around the hooks, not bypassed.** The scan runs under the lock before any
hook and binds the registration the removal will act through; the removal of the checkout, the administrative
directory and the prune take the lock again inside the funnel, after the `Before` hook, and release it before the
`After` hook (`remove_worktree_proving`, the new private `remove_bound`). A lock-free inventory path for observers
would serve an observer that reads on the holder's own thread and nothing else: a hook that waits on another
thread's registry access would still deadlock, and the rule that a holder calls out to nothing would stay broken.
The add/prune race stays closed: every add, list, scan and prune runs under the lock, so none sees another half
done; what the split admits is a *complete* add of another slot between the scan and the removal, which the prune
under the lock leaves alone (its checkout exists), and a change to the bound registration itself is what
`registration_still_names` already handles. **A first version re-scanned inside the funnel** and bound after the
`Before` hook; three existing tests that exchange or rebind the registration at that hook and expect the
acted-through check to refuse it failed (`dev/fix5-coord-wm.log`:
`a_registration_admin_directory_exchanged_at_the_before_hook_refuses_the_worktree_removal`,
`a_registration_rebound_after_validation_keeps_its_admin_state`,
`every_path_a_primitive_acts_through_refuses_a_link_planted_at_the_before_hook`), so the binding stays the
pre-hook scan's.

**"Never nested", re-checked against every holder** (R-X corrected in §3): the add's Git child (inside the funnel,
after `Before`, released before `After`); the removal's scan; the removal's mutation (filesystem calls,

#### `R1-CONC-3` — a non-halting decline leaves `verify` waiting for ever

**The finding**: "While verification V remains running, the coordinator ingests a decline with
`decline_halts_run = false`. The fold closes that lineage and removes V's transaction. The coordinator neither
cancels V nor unwinds its verification wait. When V eventually reports, `check` correctly detects the closed

**Constructibility.** The live engine of this build cannot produce the sequence. It runs at most one member of a
lineage at a time: a repair is spawned only inside a `merge_rejected` (the only `task_spawned` producer is the
tests' `scaffold::Run::spawn_repair`), a repair is dispatched only from the rejection that names it

`check_attempt_started`, and queue eligibility through `task_is_awaiting_input`). So neither a decline nor a lineage
member's failed settlement finds another live member to close. The fold admits the state all the same (its
`declining_an_embedded_question_cancels_its_lineages_unprepared_verification` and
`declining_an_embedded_question_closes_a_running_sibling_and_refuses_its_late_result`), the design requires it
handled, and PR12's writer may reach it; so it is constructed, with the observer seam `Release::Append` — the
test's scheduler plants a recorded event at a quiescent point, fold-checked, appended by the coordinator — planting

**The witnesses.** `a_declined_embedded_question_stops_the_verification_its_lineage_had_started`: beta's candidate
under verification, its gate held; the sibling parks; gamma's worker ending opens the pass that ingests the
decline. **Red at `898e7338`**: with gamma's candidate ready, the coordinator selected gamma's integration inside

**The repair.** `reconcile`, first in every admission pass (after the poison check, before the ending check —

#### `R2-CONC4-1` — a halt publishes a verification whose result had arrived

**The finding** (concurrency lens, verbatim in part): "Gamma is parked on a question; alpha has merged; beta's
verification is the only remaining pipeline. Beta sends `Verified`; the coordinator retires it and retains its
judgement in `arrived`. The next admission pass receives Gamma's halting decline. Because `live` is now empty, the
guard skips `halt()`. `verify_concurrently` returns the retained judgement, and integration prepares and publishes
it. … Closure step (2) requires interrupting the still-open `VerificationStarted` transaction."

**The witness**, `a_halt_after_the_verifications_result_arrived_interrupts_it_and_publishes_nothing`: gamma parks
on a question and alpha merges; beta's verification is then the only live pipeline (asserted when its last process,
a review, is released). The answer source, `DecliningAtPoll`, is armed at that release to decline at the second poll.
The deterministic intake applies the review's end and then the verification's completion, each followed by one
admission pass, so the decline is ingested in the pass after the completion was accepted. `discarded() == 0`
confirms the completion was accepted, not discarded as a cancelled pipeline's. **Red at `e6ecc64d`**: after
`question_answered` the log reads `merge_prepared`, `task_merged`, `run_finished`
(`repro/final-2495300c/a_halt_after_the_verifications_result_arrived_interrupts_it_and_publishes_nothing.log`; the
reviewer's witness gives the same sequence, `repro/reviewers-e6ecc64d/`). **Green at `2495300c`**:
`question_answered`, `merge_verification_interrupted`, `run_finished`. Nothing was prepared or merged for the
sequence, every process of the verification ended `Completed`, the pin was deleted expected-old, and the staging and
the sequence's snapshots were reclaimed before `run_finished`. The ledger balances with no duplicate, and the replay
equals the live fold.

**The root cause.** The admission pass decided whether a halt had anything to interrupt by the live table
(`halted && !self.live.is_empty()`). A verification whose completion has been accepted has no pipeline, but its
transaction stays `VerificationStarted` until `integrate()` appends a terminal, so the fold still shows it in
flight. Nothing else stood between the accepted result and the prepare: `verify`'s loop checks for an interrupt
before it looks at the arrival, and none was recorded.

**The repair.** `any_in_flight`: a halt is acted on when a pipeline is live or the fold shows in-flight work
(`closure::in_flight`). In the arrived window that is the verification. `halt()` records the interrupt, `verify` ends
`Interrupted` and records the sequence as cancelled (as it does for every interrupt; R-AF's vouching), `integrate()`
appends nothing further, and the closure appends `merge_verification_interrupted` and reclaims the pin, the staging
and the sequence's snapshots. The pipeline had ended, and each of its invocations had reported an end that
established its process gone — an unresolved one would have ended the command first. The terminal's detail text
said "the coordinator cancelled its pipeline … nothing was judged", false in this case; it now says the pipeline had
ended, cancelled or with a result the halt discards unprepared (`closure.rs`, `InFlight::interrupted`). A budget stop
is not a halt: it drains, and an arrived verification reaches its natural terminal as before
(`a_verifications_review_spend_is_charged_before_the_next_selection` still asserts its `merge_prepared` after
`budget_exceeded`).

**The class — every place that takes "no pipeline is live" for "nothing is in flight"** (`measure/class-search-in-flight.txt`,
the production region's every read of the live table, the arrival and `in_verify`, at both heads):
- the halt check in `admit` — repaired;
- `drive`'s idle arm (`live.is_empty()`, then `idle()`): `verify` is never on the stack there, so every in-flight
  identity this coordinator started has a live pipeline; the idle closure vouches for nothing, and anything else in
  flight is refused by `closure::settleable` before any append;
- `cancel_all` records the cancelled identities from the live table, and `finish` drains it: the arrived
  verification is recorded by `verify`'s `Interrupted` arm, for every interrupt;
- the budget stop's drain decision (ending and not halted: nothing cancelled): a drain, correct as it stands; a budget
  stop converted to a halt goes through the repaired check;
- a shutdown and an append error: each records its interrupt unconditionally, and `verify` checks the interrupt
  before the arrival, so no arrived result is returned after either; each ends the command appending nothing, and the
  next process's recovery settles the transaction (R-AJ, R-AI);
- `verify`'s abandonment (`!live.contains_key(&pipeline)` once the transaction is gone): it asks the fold first.

**The mutation** `r2-conc4-1-live-only-halt` (the check back to the live table alone): the witness fails with left
`["question_answered", "merge_prepared", "task_merged", "run_finished"]`; the module's other 48 tests pass

#### `R2-DECLINE-QUEUED` — a decline aborts the command when another candidate is queued

**The finding** (delta lens, verbatim in part; the concurrency lens found the same): "Start beta's verification,
park its sibling on an embedded question, and let gamma finish into the candidate queue **before** accepting the
non-halting decline. The decline removes beta's transaction. `admit()` reconciles its pipeline but continues
selecting: gamma is now eligible, while `in_verify` remains set. The command fails with 'selection returned an
integration of task 2 while a verification is open,' before reaching the new abandonment check."

**The witness**, `a_decline_that_cancels_the_open_verification_goes_on_to_integrate_the_queued_candidate`: round
R1's verification witness with a fourth task, delta, whose worker ending opens the pass that ingests the decline. So
gamma's candidate is queued before the decline (asserted: its `task_candidate_created` precedes `question_answered`)
while the verification's gate is held (asserted when the decline is armed). **Red at `e6ecc64d`**: the command ended
with the reviewer's refusal. **Green**: the verification's gate was cancelled and nothing was appended for its
sequence after the decline. Gamma's queued candidate was integrated next (its `merge_prepared` and `task_merged` after
the decline), and the abandonment warning was recorded. Alpha, gamma and delta merged; the ledger balances, and the
replay equals the live fold.

**The root cause.** Round R1's `reconcile` stops the verification in the pass that ingests the decline, and `verify`
unwinds when its transaction disappears — but the pass itself went on. With the transaction gone,
`eligible_integration_candidate` returned gamma's, and the integration arm's refusal (one transaction at a time)
ended the command. Round R1's witness had gamma's candidate become eligible only after `verify` had unwound, so it
never met the refusal.

**The repair.** `abandoning`: while `verify` is on the stack and the fold no longer holds its transaction open, the
admission pass ends — after the reconcile that stops the pipeline, and after the ending check, so a halt in the same
append still cancels at once — before ingestion or selection. `verify` then waits for its pipeline to end and
unwinds; `integrate()` appends nothing; the coordinator's `integrate` reads `abandoned` and returns to the outer pass,
which selects gamma. `in_verify` now carries the verification's identity, so the pass can ask the fold.

**The class — every append that can remove `verify`'s transaction, and every selection made under `verify` after it
is gone.** The appends are an ingested decline (in the pass), a lineage member's failed settlement (in `handle`,
before the next pass) and a planted event (the test seam), and each is followed by an admission pass that now ends
at `abandoning` before anything is selected. The selections are the integration (the finding), a retry, a dispatch,
a budget stop and an answer's ingestion, all after the check. Round R1's claim that `R1-CONC-3` was repaired is
corrected in its subsection above and in R-V (§3).

**The mutation** `r2-decline-queued-no-return` (the early return removed): the witness fails with the refusal; the
other 48 pass.

#### `R2-RECONCILE-GRANT` — reconciliation grants another closed pipeline while withdrawing the first

**The root cause.** The broker grants by its queue alone and knows nothing of the fold, and the coordinator handed
